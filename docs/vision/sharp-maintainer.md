我的创造欲又被点燃了……其实我挑战过几次写自己的LLM agent runtime，还碰了不少壁，但也积累了经验。我现在觉得市面上主流的这些……都有巨大的改进空间。项目上不上另说，我先和你聊聊我的思路吧。首先，我认为“把LLM session作为一次性耗材”这事儿就太原始，建立认知是要代价的（花时间、花钱、有建立错误认知的风险），在开发过程中形成的深度认知是有价值的。我也承认，当前任务具有局部性，但那完全可以用某种显式构建的上下文状态来建模，管理起来，而不是每次现创建和用完直接丢弃。我说的比较抽象，把抽象理念投影到具体的工程设计上，可以是形成一个“认知graph”，每个认知是一段带有depends_on列表的文本，标注这段认知成立所依赖的其他认知，叶认知则是{源码、目标文档、实验记录、外部资料}，记录哈希和追踪变化，当基础认知内容变化时，沿着依赖链把受影响的部分都标为“待核验”，这样让LLM可以通过diff查看变化并维护认知图谱。关于树形思考，subagent任务闭包很理想，但现实是要subagent的创建者说清楚上下文的代价不低，而`gpt-6-astra`用默认fork-all-turns已验证了总成本具有竞争力（subagent共享parent session的prompt cache不必再支付一份prefill钱，还可以在fork时创建parent history部分压缩的快照），特别是在astra的token单价其实非常贵的情况下（`https://artificialanalysis.ai/models/comparisons/gpt-6-astra-high-vs-glm-5-3` AA的比较表格，只读任务让`glm-5.3-flash`的subagent帮你读关心的信息就行，少占你自己的上下文）；树形思考的主要风险在于“沿着错误认知不断强化，缺少自我怀疑”，这事儿在当前这代模型中已大大缓解，而且还可以通过提示词工程显式引导，比如fork到子任务时提示一句“过去形成的判断不一定完全可靠”。在廉价fork方面，我经过几次重写，为多年寿命的LLM Agent系统写了个`"E:\repos\Atelia-org\durable-graph\README.md"`,最初动机就是解决json lines的不足，fork廉价且容易，而且可以让session实现盘上状态机，流程/调度状态不依赖内存瞬态，可以更细粒度的从偶发故障中透明恢复。关于LLM与源码的互操作，我认为目前基于文本的做法有局限，更好的做法是让agent runtime与dotnet Roslyn紧密协作，不只是工具调用，也包括runtime主动的动态上下文注入和维护，让更多功能在源码语义图上进行而非文本级别进行，比如查找调用链，比如rename。文本编辑的精确历史占据大量上下问窗口，这事儿也有很大的改进空间，可以管理起来，比如单个文件只保留最新状态和有限的编辑历史，太久远的确实用不着，用watch/attention语义。这样让LLM上下文中append-only那段历史短一些，前面的稳定“project-understanding”和尾部动态变化的“project-live-state”（现在的项目里根本没有这部分）长一些。还有读文档、读网页、读代码等，根本不该看完详细内容后全部记住，而是引入micro-wizard机制，显式提取出“要放入工作记忆”的部分，然后忘掉其他内容也忘掉这个显式提取的过程，主线session里只留下“我为了某事看了某文档，记住了谋内容”这个最初的目标和结果，从源头提高上下文窗口（工作记忆）的利用率，而不是“先污染后治理”模式。关于依赖roslyn后绑定C#和dotnet，首先这一个领域“集中一点，登峰造极”对我来说也足够了，其次在处理其他源码时可以回退到文本模式嘛，以后也许能接入其他语言的LSP Adapter实现某种“部分降级”模式。其中大多数局部设想，都有旧项目的专项探索，但没有整合在一起。以上就是我看到的远景和技术路线了。你自己咋想？
