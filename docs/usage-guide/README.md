# DurableGraph 使用指南

面向正在选择持久化方案、设计领域模型的应用开发者和 Coding Agent。
先判断应用是否适合，再选择模型和恢复协议，最后接入 API。

**推荐起点：让一个工作副本拥有可变的领域对象图，在明确的业务边界提交；
由 DurableGraph 捕获独立的版本化状态、比较变化并维护可恢复的历史。**
应用不必为了保存历史，把每一次业务更新写成不可变对象的路径复制。

本指南的首版于 2026-10-21 对照源码 `5227d05` 编写。它提供应用设计建议，不新增产品合同或性能承诺。
可执行接入步骤以[根 README](../../README.md)为入口，实际能力以
[产品工作集](../../src/PROJECT-STATE.md)、源码和对应测试为准。
DG 仍是 API/格式未冻结的 .NET 10 原型；采用它时应固定并验证实际使用的包。

## 适用判断

当以下特点同时出现时，DG 值得优先做一个小型接入实验：

- 核心状态能表达成受支持的强类型 C# 对象图，业务中存在对象关系、共享引用或循环引用。
- 应用需要保存当前结果、冷启动继续、查看历史，或者从某个历史节点分叉。
- 一次业务更新可以由明确的 owner 串行完成，并在捕获期间保持对象图稳定。
- 单次提交可达的活跃状态规模可控，允许用扫描与比较换取领域更新代码的简单。
- 应用愿意显式维护 Schema 演化、恢复后的资源重建及外部副作用策略。

以下场景需要先证明适配性，或把 DG 放在较窄的边界：

| 场景 | 需要先回答的问题 |
| --- | --- |
| 每秒大量模拟 step、极大数组或世界图 | 每步都要持久提交吗？捕获、比较、分配和发布是否在实际预算内？ |
| 数据主要用于跨实体查询、报表和大量独立行更新 | 是否仍需要数据库作为查询或业务事实的主要存储？DG 承载哪一部分对象世界？ |
| 多个 writer 同时编辑同一世界 | 如何划分所有权和协调更新？当前 Repository/WorkingCopy 不能直接充当并发事务系统。 |
| 主要状态藏在原生引擎、GPU、Python 对象或远程服务中 | 能否导出和恢复必要状态？只保存 C# 外壳是否足够？ |
| 希望原样恢复 Task、调用栈、Socket、OS 进程 | 能否改为保存显式阶段和恢复所需数据？DG 不保存这些执行资源。 |
| 核心要求是外部副作用只执行一次 | 外部系统如何提供幂等、查询或事务能力？对象图保存本身不能完成这个保证。 |

DG 可以与数据库、文件存储、模型服务并用。选型时写明每一项事实由谁负责，
避免两个后端都被当成可独立更新的权威状态。

## 三类应用的切入点

下表是架构判断，不是已有产品的吞吐或生产可靠性验收。

| 应用 | 推荐先保存的内容 | 首先验证的边界 |
| --- | --- | --- |
| 长寿命 Agent | 目标、计划、任务依赖、执行阶段、已知模型/工具结果、待处理输入 | 活跃 State 是否持续膨胀；结果未知的外部操作如何继续 |
| 回合制、剧情型 RPG | 角色、物品、任务、关系、逻辑时间及必要的随机状态 | 跨对象不变量；旧规则下保存的世界如何在新程序中打开 |
| RL / Gym 类环境 | 完整模拟状态、必要的 PRNG 状态、步数、待处理动作及实验配置 | observation 是否遗漏内部状态；恢复和分叉的成本是否适合训练循环 |

实时 RPG 也可以只在业务存档点保存权威状态，将渲染和可重建缓存留在运行期。
RL 的每一步计算与持久提交不必一一对应；提交频率由恢复、分析和实验需求决定。

## 先避免三个默认假设

1. **“用了 State/Event 分离，就必须写纯函数 reducer。”** 状态机可以确定性地原位更新。
2. **“用了 DG，就必须先设计事件账本。”** 连续保存 State 已经是完整的使用方式。
3. **“能冷加载，就已经证明能继续执行。”** 还需验证 Transient 重建、待处理阶段、外部资源和新一次保存。

从[心智模型](mental-model.md)开始，或者直接用[接入与验收](adoption-and-validation.md)规划最小实验。
