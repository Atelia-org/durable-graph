# 应用建模

[使用指南入口](README.md) · 前置：[心智模型](mental-model.md)

## 先定义恢复后必须知道的事实

用一个具体问题划定 State：进程完全退出后，新的进程需要知道什么，才能作出下一步业务决定？

| 类别 | 常见内容 | 建议位置 |
| --- | --- | --- |
| 权威领域事实 | 角色 HP、物品归属、任务进度、Agent 的目标与计划 | Durable State |
| 执行进度 | 当前阶段、待执行操作、关联 ID、最后应用的事件序号 | 需要恢复时放入 Durable State |
| 历史事实 | 用户输入、模型响应、工具结果、世界中的重要发生事项 | 按需保存为 Event；当前决策所需部分进入 State |
| 可重建派生数据 | 查找索引、缓存、UI 投影 | Transient 或图外对象，恢复后显式重建 |
| 外部执行资源 | HTTP client、CTS、Task、进程句柄、Socket、渲染资源 | 运行期宿主；保存必要描述，不保存资源本身 |

“可重建”必须有具体来源。某个摘要若来自一次不可复现的模型调用，且未来决策依赖它，
不能仅因为它看起来像缓存就丢弃。相反，能从持久事实确定性算出的索引，通常无需成为另一份权威状态。

## 让一个 owner 管理工作副本

一个简单应用可以分为：

- **领域模型**：事实、业务身份、规则和不变量。
- **更新程序**：验证输入，原位更新领域模型；不执行外部 I/O。
- **持久会话**：拥有 Repository/WorkingCopy，负责串行提交、故障后停用与重开。
- **I/O 驱动器**：根据已保存阶段调用模型或工具，把返回值作为新输入交回会话。

这是一种组织建议，不要求建立四个程序集或通用 Agent 框架。
小应用可以只有几个类，也不必一开始就加入 Event。
状态机与持久会话的关系见[提交、事件与恢复](events-and-recovery.md)。

同一 Repository 的操作串行执行；每个 BranchId 至多一个活动 WorkingCopy。
同一个工作副本内不要让 UI、后台线程和工具回调同时修改对象。
先把结果送入 owner 的输入队列，再由 owner 在一致性边界更新和保存。
异步 I/O 期间可以释放执行线程，但仍须保持这份状态的逻辑所有权。

## 业务身份与保存身份分别使用

DG 在一份图中保留共享引用和循环引用。同一个角色可以同时由角色表、队伍和任务引用，
不必仅为序列化方便把所有边都改成字符串 ID。

跨进程消息、Event 到 State 的定位、外部服务关联则应使用显式业务 ID。
例如 Event 保存 `ActorId`、`Damage`，需要当时观察值时再保存 `ObservedHp`。
冷加载 Event 后，用 ActorId 在当前 State 中查找角色；不要期望 Event 中的角色实例
与 State 中的角色实例是同一个 CLR 对象。

ObjectId 是保存机制的身份，不是应用全局主键；尤其不同 Event 的同号 ObjectId 不表示同一对象。
业务值相等也不会让两个独立实例自动合并。record 的 `Equals` 和 `with` 不改变这个规则。

在已有对象上修改字段、调用已有 List 的 Add/Remove，通常更符合 DG 的身份与增量路径。
若业务上确实发生了对象替换，就直接替换；不要为了保持 ID 伪装对象生命周期。

## 完整更新以后再提交

物品转交的一次业务更新，可能同时改变：

1. 原所有者的背包；
2. 新所有者的背包；
3. 物品的 Owner 引用；
4. 相关任务进度。

如果这四项共同构成业务不变量，就在四项完成后提交同一个领域根。
捕获和其他读取不应观察中间不一致的图。
提前校验常规拒绝条件；更新中途异常则按[失败处理](events-and-recovery.md)停用可能已部分修改的工作图。

领域根表达一次保存需要的完整可达状态，不要求类型名必须叫 World。
先用一个业务分支和一个根跑通。只有具体场景需要不同世界、分叉或独立保存单元时再拆分；
多分支共同发布也不提供外部系统事务，API 见[根 README](../../README.md#多分支共同保存)。

## 持久字段与恢复后的初始化

按当前模型合同声明 DurableType/DurableField；具体受支持类型以
[根 README](../../README.md#当前能放进模型的内容)为准。
不要因为某个 CLR 类型可以被 JSON 序列化，就假设它可直接进入 DG 图。
普通 class 的入门形状优先使用显式字段，需要封装时另加方法或包装属性。

**恢复不运行领域构造器或字段初始化器，也不自动调用 Transient 重建 hook。**
因此，下列初始化流程都需要明确安排：

- 重建按业务 ID 的索引，再执行依赖索引的领域方法。
- 从持久事实初始化派生缓存，完成后才向 UI 或业务驱动器交付。
- 重新创建客户端、工具会话和取消控制器，绑定到恢复的领域阶段。

只把一个字段标成 Transient 不会自动让它可用。构造器中的 `new Dictionary<...>()`
不能代替冷加载后的重建步骤。
保存后继续编辑应使用工作副本交付的 State；不要把创建初始分支时传入的旧根当成当前工作图。

## 活跃 State 与长期历史

长期应用可以拥有很长的历史，同时只让有限内容参与每次 State 捕获：

- Agent 保存当前目标、尚未完成的任务和决策所需上下文；旧事件按需浏览。
- RPG 保存当前世界事实；历史回合可以保留在提交历史中。
- 模拟环境保存当前内部状态；轨迹分析按实验需求另行读取。

将无限增长的历史 List 挂在当前根下，会让这些元素继续属于每次捕获的可达图。
磁盘上的 Delta 可能很小，但活跃图扫描、冻结和比较成本仍可能增长。
是否保留全量历史引用，应依据实际业务需要和测量决定。

从当前 State 断开引用不会删除旧 Commit 中的事实，也不等于回收历史磁盘空间。
历史保留、容量规划与未来可能的清理能力须分别确认；不要把应用投影裁剪解释成存储压缩。
历史 UI 优先使用提交 Summary 和 ReadHistoryPage，再按需加载正文，
避免为了显示最后几十条记录而恢复全部 Event。

## RL、RPG 和长寿命 Agent 的补充

对 RL，observation 是对策略暴露的观察，不一定包含继续模拟所需的全部状态。
具体环境可能还需 PRNG 当前状态、逻辑时钟、wrapper 的步数/截断状态、延迟动作和配置。
保存初始 seed 并不等于保存已经前进的随机数序列位置。
若要求训练过程整体续跑，还需另行安排 learner、优化器、采样器等状态；环境存档不是完整训练 checkpoint。

Gymnasium 明确维护环境 PRNG，动作空间采样也有独立 seeding 入口。
MuJoCo 的精确复现要求完整 integration state，并限制在相同版本和架构等条件内。
这些资料说明“必要状态闭包”必须按环境确认，不证明 DG 已可直接保存其原生类型。
见 [Gymnasium Env](https://gymnasium.farama.org/api/env/) 和
[MuJoCo Reproducibility](https://mujoco.readthedocs.io/en/stable/computation/index.html#reproducibility)。

RPG 可以保存逻辑世界，把渲染、音频、导航缓存留在运行期。规则升级后，旧事实如何解释、
从旧存档继续采用哪套规则，要与字段布局升级一起考虑。

长寿命 Agent 应显式保存 Awaiting/Ready 等阶段和关联数据。
“曾经发出请求”与“结果已经保存”是不同事实；
进程恢复后不能仅凭一条日志就推断外部操作成功或失败。
旧进程句柄和工具 session ID 的有效期也需要由工具/宿主定义。

## 分叉的用途与限制

ForkBranch 从准确 Commit 建立新分支；OpenWorkingCopy 再恢复新的工作对象。
它适合另开剧情、比较策略或从某个实验节点继续。
持久历史的共享不意味着内存世界可以零成本 clone；恢复和物化仍有成本。

如果分叉点是 Event，签出只恢复最近 State，不自动应用该 Event。
应用须决定分叉的是“这个历史位置”还是“已处理该事件的业务状态”。
分叉也不会复制远程服务或撤销已经发生的工具副作用。
具体分叉、切换与摘要配方见
[已有应用配方](../design-branches/0096-history-and-head-model/application-recipes.md)。
