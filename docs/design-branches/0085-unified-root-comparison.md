# DB-085：统一系统根与现有发布协议的对照

> 状态：产品方案仍为候选；2026-09-30，[首个固定双值机制实验](0085-unified-root-experiment.md)已完成并通过独立验收，根统一选择和有界读取成立，保守 writer/恢复仍全量扫描。随后[目录/单次轮转对照](0085-unified-root-metadata-experiment.md)也已验收，确认候选可替代三套独立发布权威，同时记录完整目录复制与全量资格成本；真实 DG Schema/State/Journal 接缝仍待证，尚未选择 DG 新格式或修改产品路径。下文保留 2026-09-29 的认知来源，原 [S0-D](0085-s0d-cli-rescue-implementation.md)及此前验收仍有效。

## 1. 问题与需求来源

用户建议：每个子部分提供可寻址的状态根，父层引用子根，最后由 DurableGraph 发布系统根，使多文件变化共同生效。要判断的是它能否减少整个系统的权威与恢复规则，同时保持易用性、持久性、性能和合理复杂度。

| 约束 | 来源与适用性 |
|---|---|
| 两仓无外部用户，唯一内部旧数据已升级；没有通用兼容框架需求 | 用户已明确；允许讨论 breaking 重构，不等于已授权迁移真实数据 |
| 单 writer、串行操作、仓库独占；完整已确认提交不丢，已发布损坏不静默回退 | 当前代码及用户持久性目标 |
| Normal 避免无关历史全扫，恢复可以自动执行并报告，Audit 独立全量诊断 | 用户已确认的三路径目标 |
| 强保证绑定受控 FS/OS/硬件及真实 writer 协议 | 用户允许定制栈；尚无平台断电证据 |
| S0 保留全部完整事实和 orphan；旧 Store/cache 关闭后才能离线修尾 | 已实施片与 AGENTS 的当前约束；不推导为未来 orphan 永不可回收 |
| 各层独立发布、无全仓提交根 | DB-085 原路线的设计选择，不是禁止新方案的用户定律 |

2026-09-29 的授权仅为认知与文档沉淀；用户于 2026-09-30 授权的首个最小实验已按[施工记录](0085-unified-root-experiment.md)完成。下述建议保留形成过程，当前状态以施工记录与 PROJECT-STATE 为准。旧的“先做轮转合同”提示词不再作为默认续工入口。

## 2. 候选的最小模型

系统根选择整个仓库的一致视图，不是某一个业务 State 的图根，也不把分支 DAG 改成线性业务历史。概念形状可先固定，不建设任意递归的事务参与者框架：

```text
RepositoryRoot n
  -> SchemaView
  -> StateView
  -> JournalView（含 branch/tag/ref 和段定位的确定版本）

写新增数据及子根
  -> 确认新纳入的依赖及其文件名持久
  -> 发布并持久化 RepositoryRoot n
  -> 返回成功
```

只有最外层根决定本次整体变化是否进入业务视图。子层可产出候选地址，但不能在同一事务中另以“各自最新”决定对外状态。standalone EventJournal 若仍需要独立提交，可让它在自己的使用场景担当最外层；是否需要这种组合 API 尚待真实消费者核对，不先建双模式框架。

根必须固定全部相关依赖的版本及边界。文件继续追加可以成立，**不可变的已提交范围（extent）足够，不要求整个文件永久冻结**；按旧根读取不能穿过其可见 EOF。根自身的定位、部分写入、完整损坏及旧根保护仍须独立定义，append 并不天然原子。

## 3. 为什么可能更简单，以及当前代码缺什么

当前 [Repository.Publish](../../src/DurableGraph.Persistence/Repository.cs)在 State/Journal 之后通过 branch ref 发布；[SegmentLocator.Publish](../../../atelia-storage/src/RbfSegmentStore/SegmentLocator.cs)替换 `active.segment`；[EventJournal.CheckpointCatalog](../../../atelia-storage/src/EventJournal/EventJournal.Refs.cs)替换目录快照。根若继续引用这些文件的“最新内容”，旧根也会观察新状态，不能建立一致版本。

[CatalogSnapshot](../../../atelia-storage/src/EventJournal/CatalogSnapshot.cs)包含名字到 RefId 的目录和 tag，但没有冻结所有 ref 的当前 head；[SchemaStore](../../src/DurableGraph.Persistence/SchemaStore.cs)的普通打开按实际日志重放。现有结构尚非完整的不可变子根。重构必须改变版本选择权威，不能只在旧发布链后追加一个总日志。

| 责任 | 初步判断 | 成立条件 / 不可省的部分 |
|---|---|---|
| locator、ref、catalog 各自决定“当前” | 合并为根选择的确定视图 | 所有对应读取都受根约束，旧根解释不变 |
| Create/Bind、Close/Archive 等中间态的联合补发布 | 有机会简化 | 未被根发布的中间态不得独自进入业务视图；不是删除业务生命周期语义 |
| 为采用残留完整记录而遍历所有 orphan 依赖 | 有机会从 Normal/恢复快路径移出 | 首片不重新采用根外孤儿；Audit 仍报告完整物理事实及适用依赖 |
| 校验、独占、依赖屏障、旧范围保护、再次中断 | 保留 | 统一根改变提交判据，不产生设备持久性保证 |
| 任意嵌套事务框架、通用 WAL、GC、兼容层 | 延后 | 当前对照不需要；不因结构可级联就全面泛化 |

固定顶层 tuple 不代表下面的元数据很小：冻结所有 ref frontier 可能需要 O(分支数) 快照或 CoW map；另一候选是统一操作流加 checkpoint/确定 suffix 边界。必须测量提交写放大、flush、启动与首次读取、失败残留增长，不能只按恢复代码减少判定成功。

## 4. 必须保留的反例与语义

1. **根已发布但名字丢失**：新段内容写好，系统根持久并回包，断电后新段目录项不存在。不能退旧根来掩盖已确认提交丢失；新名字/目录的持久顺序属于平台合同。
2. **可变元数据破坏旧根**：R0 引用固定文件名的 catalog，先覆盖 catalog、未发布 R1 就中断；R0 已不再选择原状态。须引用不可变版本，或将 locator/catalog 降为不拥有权威的提示。
3. **可读的未确认孤儿被重新采用**：D 写完未 flush 就中止，重开读到 D，直接发布引用 D 的根，再断电丢 D。新纳入根的依赖须确认；首片直接不复用根外完整 orphan。
4. **完整未回包根**：若真实协议先成功持久化全部依赖，再开始写 R1，完整 R1 可证明下层已过屏障，但不能证明 R1 自身 flush 已完成。后继依赖它时仍需确认；同文件最终 flush 可覆盖两代，换文件不能省略旧根文件及名字的确认。不能按“应用未收到成功”删除 R1。
5. **已发布损坏被降级为未完成**：完整坏根，或所选根引用的数据损坏，必须按故障模型明确拒绝。不能不停搜索旧 CRC 好的根直到能够打开。I/O、取消、预算耗尽也不能触发这种回退。
6. **逻辑可读但不能续写**：R0 可限定到旧 EOF，物理文件却留有半帧；直接在坏尾后继续追加会留下中部损坏。需要离线局部处理，或新段绕开，并证明恢复再次中断仍可重试。
7. **保留孤儿与身份冲突**：从旧根恢复的 Schema/RefId/段号分配器不能撞上仍保留的物理事实或已交付地址。根不自动解决高水位、文件身份或外露地址寿命。
8. **根定位重新引入全扫**：无限增长的根日志若每次从头找末条，启动仍随历史增长；根记录的有界定位和根日志自身轮转要计入完整方案。

完整 orphan 可先保留并与业务视图隔离，GC 不必成为首片前置。现有 EJ CAS 失败会交付 `OrphanEventAddress`；任何以后删除/重用这些记录的方案，须先核对其地址承诺，不能仅凭当前 head 不可达获得资格。

独立质疑后收窄了两项初始推断：不宣称系统根能立即删除全部尾处理；也不默认每次失败都换新段。换段会新增身份分配、文件名持久化、残留目录和段视图增长，须与局部离线处理比较。保守重确认可以依据已证明的根发布因果关系缩窄，但不能仅凭读到根就删除所有屏障。

## 5. 业内依据及证据强度

- [LMDB 作者设计说明](https://www.snia.org/sites/default/files/SDC15_presentations/database/HowardChu_The_Lighting_Memory_Database.pdf)，Transaction Handling（PDF 第 82–83 页）：先写并同步数据页，再同步根元数据。支持“最后发布根”的机制依据，不直接证明 DG 的多文件/目录实现。
- [OpenZFS txg 源码说明](https://github.com/openzfs/zfs/blob/master/module/zfs/txg.c)：以新 uberblock 表示事务组完成后的池状态根。仅作架构先例，不把使用 ZFS 等同于本应用已经具备跨文件事务或断电保证。
- [SQLite Atomic Commit §5](https://www.sqlite.org/atomiccommit.html#_multi_file_commit)：rollback-journal 模式用 super-journal 建立多文件共同提交判据；具体实现与 CoW 根不同，不能泛化为 WAL 模式的相同保证。

以上在 2026-09-29 核对。上一轮以需求质疑、最小架构和语义防守三个独立视角审查，交叉质询后的结论是“值得先对照”，不是新格式验收，也没有新性能或故障实验数据。源码与 S0 测试证明现有基线，行业先例只证明模式有成熟基础。

## 6. 首片建议与停点（已实施）

本节的固定双值首片已实施；结果与后继停点见[实验结论](0085-unified-root-experiment.md#结论与下一交付)，不重复启动本节。

原建议先明确两路线的责任差异：现有分层发布/协议恢复 vs 单一系统根/版本视图。收口“根字段或子视图 → 覆盖的事实/依赖 → 何时持久 → 谁可发布 → 重开如何选择 → 拒绝反例”合同。

最小机制实验建议使用独立新夹具、已初始化的单 writer、两个依赖文件和固定形状系统根，完成一次共同更新；保留完整 orphan，先验证逻辑隔离，不迁移 DG 格式。至少证明：根前中止仍见旧一致视图；根完成但回包前中止按协议选择；已确认提交不丢；根/依赖损坏不回退；恢复再中止后能续写并冷开；源外未知内容不被自动清理。真实写入故障注入、外部 kill 与 F2 模型分开。

输出不能只是一段成功 demo：必须交代根定位、物理坏尾后的下一次写入和身份不复用。测量完整提交/屏障成本、Open + 首次读取，并分别改变历史与未提交残留量；报告请求/返回/预取、耗时、线程分配及预算边界，不把进程冷开称作 OS cache 冷。

**首片停点**：给出可执行对照与推荐，明确支持/否定/尚不能判断的部分；不切换公开 Open/writer/Audit/rescue，不冻结通用 API。随后只有在机制成立时，再引入两个分支或 tag 中一种及一次轮转，检验它能否真正替代 catalog/ref/locator 权威、是否隐藏全目录复制成本。两文件成功不等于全产品更简单。

S0 的帧解析/CRC、固定 EOF reader、共同 validator、独占与全新资源纪律、kill/再中断宿主继续复用。S0 的保存规则不因候选文档自动失效；产品迁移、完整生命周期和 S2 平台门仍需单独取得证据。不要按沉没工作量选择路线，也不预先铺开大量新分片。
