# 可登记叶对象的可行性与保存成本

主线提交 `c3478351` 优化了内建 `DurableText`；研究分支 `research/db104-registered-leaves` 使用同一文本算法作为对照。可登记的无出边类型已经跑通独立包、生成模型、真实落盘和全关冷开。测量支持保留片表的增量优势，也显示了注册和图规划的托管分配差额。本文记录研究分支的可行性实验。正式协议、主线退役与最终包验收见[主线迁移](mainline-results.md)。[设计与备选](README.md) · [早期片表来源对照](evidence.md)

## 主线基准

准确前驱路径从冻结的 `ReadOnlySpan<TextPiece>` 按下标读取，一次扫描识别连续的 Copy 或 New，直接交给现有编码器。在 4096 单元、33 片的固定工况中，每次准确 Delta 准备从 4880 B 降至 680 B（减少 4200 B），冷回放均为 3648 B。两侧各三个 Release 进程使用相同代码，关闭分层 JIT，每项预热 900 次，测量 5 批各 3000 次。

另以 同一固定种子产生的 600 个样本逐轮编辑，分别向新旧实现提供准确基线、同版及外来前驱。两个 DLL 均逐字验证了 8400 次回放，将“变化标志、长度、Delta 字节”合并得到相同 SHA-256 `F408965661EAFDB0366750AE526523E61E9A14B7C14FBE5D41DAF87730B84E2B`。该优化与跨程序集接口无关。[热编码驱动](probes/bench.cs) · [共存版本内建编码器及其测试来源](README.md#native-text-sources) · [后继编码器回归](../../../tests/Text.Tests/TextBodyCodecTests.cs)

## 外部类型怎样进图

- 文本叶和变长位图各自由独立程序集提供，冻结状态分别持有不可变片表和自有字节。业务字段直接声明具体 CLR 类型，也可通过多个字段、List 和 null 引用。两个类型都没有实现 DG 领域对象标记。声明使用有名义 ID 和版本的公开、顶层、非泛型 sealed class；这是原型的已测范围。
- 文本包和位图包都只直接依赖已有的 `Atelia.DurableGraph.Serialization` 包，使用它及 `Atelia.Binary` 的 API。应用显式登记 codec，DG Runtime、Persistence、Generator 及 Serialization 均不引用这两种实现。程序集间通过公共合同工作，文本包保有自己的实现细节。
- 源生成器把直接字段和 List 元素标为名义引用。ABI 5 的 descriptor 路径选择准确的历史 reader。V2 实际读回 V1 的 Base 及 Delta，转换后即便没有新编辑也能强制写 V2 Base；V1 原图可以继续独立读回。缺少登记时报告具体名义类型，错误同版本布局、未消费完的载荷和不支持的版本均被拒绝。对同一 ID 和版本擅自改变私有码流含义，仍需类型作者用历史样本防错。
- 分进程保存源文本和位图、分别局改、冷开续写，再读回三代。双叶更新中的两条 Delta 各自指向准确前驱，文本 body 为 20 B，位图 body 为 `00 01 00 03`。分别打开同一图能得到互相独立的可变实例，每次打开保持本图内别名。普通包验收使用私有候选、唯一版本、单一本地源与新缓存，并核对加载 DLL 与 nupkg 的 SHA-256。

## 等算法的性能对照

环境为 Windows x64、.NET SDK 10.0.201，真实文件仓，位于同一机器。每条路径先预热，三个进程按预先排好的次序轮换两条路径；表内为各进程中位数再取中位数。分配为当前线程的托管字节。计时包含编辑及同步文件保存，因此也计入了延迟到下一次编辑的基线整理。冷开关闭原 Repository、重新打开并恢复独立图，OS 页缓存可以复用。

| 完整编辑保存周期 | 优化后内建文本 | 注册文本 | 多分配 |
|---|---:|---:|---:|
| 一条 4096 单元，8 处改写 | 0.769 ms / 59,904 B | 0.756 ms / 62,184 B | 2,280 B（3.8%） |
| 一条 65,536 单元，8 处改写 | 0.760 ms / 57,252 B | 0.750 ms / 62,492 B | 5,240 B（9.2%） |
| 128 条各 4096 单元，只改其中一条的两处 | 1.300 ms / 444,496 B | 1.275 ms / 456,088 B | 11,592 B（2.6%） |

前两行各进程、每种类型连续保存 16 次。两种长度共核对了 96 对已落盘 Delta 的字节 SHA 和各自的直接前驱，16 项 body 总量分别为 1175 B 和 1382 B。首存各编码一次文本 Base，后续热保存均未编码 Base。匹配的编码器诊断中，33 片的 Base、准确 Delta 与回放分配逐项相同。先读取两次正文再改再存的 64K 对照，注册路径额外分配为 1892 B。

第三行使用研究树上的内建类型隔离“换成注册叶”的差额。再用相同程序直连真正主线，主线为 441,480 B/周期，对应注册路径比它多 14,608 B（3.3%）。128 条全部冷开时，从研究树内建的 58.85 ms / 5,163,512 B 到注册叶的 60.79 ms / 5,401,272 B；单条 4K 正文冷开并取全文为 42.70 / 40.90 ms，64K 为 41.02 / 40.27 ms。单条与多条的冷开计时范围略有差别，多条的逐字校验和资源关闭在计时外。各成对周期与冷开耗时区间有重叠，此处的时间不能证明任一路更快。

对照曾暴露过两笔额外成本。早期外部文本每次准备 33 片准确 Delta 多 4200 B，单独换成主线的索引算法后差额消失。早期 128 叶试验热分配为 546,136 B；保持同一外部文本 DLL，只调整 DG 一侧以复用准确 Schema 的校验准备和对象布局、优化简单空 Schema 相等检查，降至 456,088 B。每次仍在当前选定的 Schema 环境中执行校验。

## 发布与复验边界

原型的框架在成功安装 State 后标记一个自身拥有的收据。文本在下一次捕获或编辑前消费；任何实际物理视图替换都清除旧凭据。Event 没有 State 收据。捕获失败、丢弃、捕获后继续编辑，以及两个图交错使用同一编辑器都通过真实回归。若多个候选在同一物理视图上交错，编辑器最多记住一个待接受收据，可能失去一次 Copy 优化，最终仍以本图准确前驱为准。

真实的发布前与安装前故障，都能关闭故障仓并重新打开，得到实际发布结果。将用户回调纳入发布后阶段，是可以另行评估的恢复策略。商定这一公共契约时，要覆盖调用方仍持有旧实例、故障前已有尚未发布的新编辑，以及如何从应用选定的持久引用恢复。可用新图恢复应用运行与保住原有 CLR 对象身份，是两个分别可验的目标。

原型实现为 `f6b62b4f`，含复现实验和归档结果的研究提交为 `049ceeb4`。主线和研究树的 Release 根构建均为零警告、零错误，根测试分别通过 3352 和 3363 项，零跳过。五个本地 DG/Text 候选包和单独的位图库使用版本 `0.0.0-leafpkg.20261119181303.gb86542b7`。

在研究提交的 `experiments/RegisteredLeafProbe/README.md` 可找到多进程 runner、三路 Fanout、生命周期/版本测试和普通包验收入口；`results/` 保留运行数据。源模式依赖所需的 Storage checkout 与包模式的六包来源见[仓库准备说明](../../storage-dependency.md)。
