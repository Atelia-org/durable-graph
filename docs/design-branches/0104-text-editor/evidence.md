# DB-104 第一片的机制对照

2026-11-20，Windows x64，.NET SDK 10.0.201，运行时 10.0.5。比较使用 `93f5ece17a57cce4b0b2dda5c5d8fea15fa7e3c0` 的产品代码。以下 Delta 数字仅为文本 body；图级策略还会决定是否采用 Delta、改写 Base 或沿用对象版本。接口归属和实施条件见[设计入口](README.md)。

## 单基线与两快照差分

对 65,536 个 `a` 做等长替换。准确来源、前后缀之间的一次替换、完整 New 三种结果均交给现行 codec 实际编码并重放，逐字与期望正文核对。

| 改成 `z` 的位置（从零起） | 准确来源 B | 最长公共前后缀 B | 全 New B |
|---|---:|---:|---:|
| 32,768 | 19 | 19 | 131,079 |
| 1,024 和 1,025 | 19 | 19 | 131,079 |
| 1,024 和 64,511 | 27 | 126,993 | 131,079 |

更强的两快照候选对准确前驱按字符串引用建立区间索引，在已知相等的前后缀以外也可以找到物理重用。重复或相交的底串切片可匹配前驱中任一确实存在的等值范围；2,000 组固定种子输入逐字重放通过。下表的两快照字节数由候选的实际操作序列按当前格式计长，单基线列使用产品的 `PrepareDelta`。

| 合成轨迹 | 单基线 B | 两快照 B |
|---|---:|---:|
| 4,096 单元的 32 片基线在接受后压成一片，再改一处 | 13 | 13 |
| 同一基线，改第 1 和 4,094 处 | 21 | 8,200 |
| 同样两处，DG 另持同版压平后的映射 | 21 | 21 |
| 对同一份冷解码的前驱恢复并改这两处 | 21 | 21 |
| 2,048 单元，同一编辑器在 A、B 两条基线上交替接受，再相对 A 编码 | 4,101 | 22 |

两个旧范围相距很远时，单基线的逻辑偏移经得起物理压平。反过来，若当前基线属于 B，A 仍共享底串，两快照候选能找回现行编码器放弃的 A 的范围。按图另存映射、内容锚点匹配、维护编辑日志都可能改善特定工况。本轮没有比较它们的整图 CPU 时间与长期驻留。[前后缀见证](probes/PrefixSuffix.cs) · [区间匹配与随机校验](probes/SnapshotDiff.cs)

## 热编码与冷重放

从固定产品源码提取编辑器到只依赖 BCL 的实验程序集，使另一个程序集里的真实 codec 只接触冻结内容、只读来源范围及冷读构造操作。原型保留分段 Base、精确 Delta、错前驱全 New、捕获后编辑拒绝安装、孤代理、超预算回退和链末大底串裁剪。101 项断言通过，其中 80 项是固定种子、每份进行七笔编辑的编码回放。完整图生命周期仍须在实施时验收。[双程序集重建补丁](probes/bridge.patch) · [可执行见证](probes/verify.cs)

4,096 单元、16 处等长替换产生 33 片，固定 .NET Release DLL、关闭分层 JIT。每个版本运行三个进程，每个操作预热 900 次、实测五批各 3,000 次，记录当前线程每次分配。主线普通 codec 与只搬运旧列表的热路径均需 4,880 B 准备准确 Delta。改用不可变片表上的只读索引计划，DG 编码器可直接完成相邻 Copy/New 的合并。[测量入口](probes/bench.cs)

| 操作 | 主线 B/次 | 推荐桥原型 B/次 |
|---|---:|---:|
| 估算 Base | 0 | 0 |
| 编码分段 Base | 13,112 | 13,056 |
| 同一版准备 Delta | 376 | 376 |
| 准确前驱，33 片 | 4,880 | 680 |
| 来源不合，写全 New | 26,360 | 26,272 |
| 冷读这份 Delta | 3,648 | 3,680 |

冷读多出的 32 B 是一个独占可变片表的引用对象。试过把它做成栈上的可变 `ref struct`。复制构造器，先用一份冻结长度为 1 的 `a`，再用另一份追加 `b`，冻结结果出现长度 1、物理内容 `ab`；写出的 Base 连原 codec 也无法读回。推荐原型统一使所有别名在成功转移所有权后失效。Copy 到一半超过片数上限时也使构造器失效，确保任何别名都不能发布残缺前缀。恰好 4,096 片仍可完成。这个区别影响冻结文本的正确性。

## 无保存编辑

纯内存轨迹在 65,536 单元正文的 2,048 个离散位置各改一个字，再对同一点改 256 次。三条路线都检查最终正文和旧快照。每个策略运行三个独立进程、轮换次序，预热一轮、实测三轮。各阶段总分配如下；128 是试验间隔。探针在每种路线都读取当前片数。

| 整理时机 | 离散阶段分配 B | 阶段末片数 | 随后 256 笔分配 B |
|---|---:|---:|---:|
| 无整理 | 101,023,744 | 4,097 | 25,223,144 |
| 仅在离散阶段完成后压平 | 101,155,040 | 1 | 57,320 |
| 每 128 笔检查，触发 16 次压平 | 8,752,640 | 1 | 57,320 |

反例是 1,048,576 单元中只改一个字，此时仅 3 片，主动强制压平还需分配 2,097,376 B。驻留也有不同于片数的情形：9 片、65,544 个可见单元，实际引用 589,824 单元的不同底串，现有最大底串与片数阈值都不会触发。显式压平后，保留旧快照仍能读旧内容，只有释放该快照后，八个旧底串才在强制 GC 中回收。[无保存轨迹](probes/Memory.cs)

另试了更通用的物理整理：将每片重切到同一份等长字符串，保留原 `BaseOffset`，按来源相容性合并，若仍是多片则缓存这份连续字符串。无来源的 `abXYef` 从 4 片变 1 片；相对 `abcdef` 的同样正文从 4 片变 3 片，两边整理前后 Delta 分别逐字节相同，旧快照还能提交非空编辑。但在 4,097 个交错 Copy/New 段上，这样整理后仍有 4,097 片，下一阶段仍分配 25,223,144 B。分段还会影响 Base 的择码：1,024 个汉字接 1,024 个 ASCII 字符，合片后真实 Base 从 3,078 B 增至 4,100 B，冷读两者均正确。为此首片只给无来源草稿研究批边界整理，已有来源的自动压平留待真实驻留数据触发。[保留来源的整理对照](probes/PreservingCompact.cs)

## 生成器、普通包与验证范围

主线空壳使用独立包源及空包缓存还原。在源码模式指向不存在的 Storage 路径、并将测试包版本设成与 Storage 版本相同的情况下，单独 pack 文本库成功。实际普通消费者加载的 DLL 只引用 `System.Runtime`，导出 0 个类型。DG 自身的错误源目录、源码模式打包和版本相同三个反例仍被拒绝。根 Release solution 构建 0 警告、0 错误，已有 3,352 项测试通过；可加载的新测试程序集有 0 个用例。

另做了仅含新类型身份的私有包实验。基准生成器拒绝新的 `Atelia.Text.TextEditor`（DG0007）。修改其准确程序集名和元数据名、给 DG 加传递包依赖，既有普通消费者的 Entry v10 与 World v9 两份 `.dgschema` 逐字节通过 Verify，含 Text 的字段仍为 ObjectReference 15、`t` 或 `l(t)`。换源代码别名仍通过，本地声明一个同名类则仍被拒绝。此时若保持旧 runtime，创建图和只读重开旧图都会在当前值绑定上拒绝新类型。这组正反例支持沿用现有结构格式；类型迁移的完成条件仍包含实际捕获、冷读与准确 Delta。[历史生成器、内建类型绑定与消费者来源](README.md#native-text-sources)

## 复跑主要对照

此见证从固定提交 `93f5ece1` 重建旧的内建文本与友元方案。先在单独工作树按该提交的 Storage pin 构建 Release 的 DG，再把 DLL 目录交给当前仓中的脚本。目录需包含 `Atelia.DurableGraph.dll`、`Atelia.Binary.dll` 和 `Atelia.DurableGraph.Serialization.dll`。原对照使用的 DG DLL SHA-256 为 `07BD18E78F5C2B61D20BB89C70A9EDB2C9C26F72E5C2DC97FC7A81FA4305A647`。Python 3.10+、Git 与 .NET 10 SDK 用于在临时目录重建。省略两个实验开关仅运行 101 项双程序集断言。[构建基准所用的 Storage 来源](../../storage-dependency.md)

```powershell
python docs/design-branches/0104-text-editor/probes/rebuild.py . --binary-directory ../db104-baseline/src/DurableGraph/bin/Release/net10.0 --alternatives --bench
```

`--alternatives` 包括两快照、前后缀、无保存与保留来源整理实验；`--bench` 比较基准 DLL 与推荐桥的分配。生成器和普通包另行验证，未纳入该机制脚本。
