# 海选评选与交叉复核

> 2026-10-25；五份独立候选已收齐，已选合同及实施入口见 [README](README.md)。本文保留选择理由与当时证据边界，不另立 API 合同。实际结果见[验收](validation.md)；本片没有实现或实测候选 C，只分解其可能适用的重复成本。

## 选择结果

采用 A 的普通 inline、非泛型 Event 根引用作为库机制；采用 E 的完整载荷所有权与发布后绑定来源；吸收 B 的显式上下文、独立恢复和应用不可变投影缓存；吸收 D 的准确历史坐标及“物理自有图不等于业务依赖闭包”区分。C 保留为真正可竞争的备选路线，并进入测量对照。

不是把五份候选的所有能力合并。新 TypeTag、统一 CommitRef、任意子对象地址、自动注入、每次保存全引用验证、通用 DTO 缓存和内容帧去重均未进入推荐首片。

## 各方案的胜例、代价与裁决

| 候选 | 最有价值的部分 | 在何种故事下可能胜出 | 本次裁决 |
|---|---|---|---|
| [A：显式根引用](candidates/explicit-refs.md) | 普通 durable inline 值足以表达持久坐标；签发、保存、读取三种验证分责 | 已有完整 Event 与 E→S 发布顺序，想直接消除正文双存 | 作为主干；补充设置载荷、缓存预算和成本对照 |
| [B：原生 lazy handle](candidates/lazy-handles.md) | 应用只在首次 miss 读取，缓存私有不可变投影；不把可变 T 全局共享 | 用户必须在字段 Schema 中约束目标类型，且需要保存前统一拒绝失效引用 | 采用读取/缓存纪律；不选新字段类型、泛型 Schema 与保存扫描。它们有更强保证，但当前用户故事没有要求为此扩大核心 |
| [C：物理字符串去重](candidates/content-addressing.md) | 业务模型不变，整串正文跨 Event、State、State-only 使用可物理共享 | 重复以相同长字符串为主，完整 State 读取性能和自有业务模型更重要 | 保留备选；需内容帧、索引、编码与故障接线，无法消除 JSON 转义子串和 RawInput 的逻辑重复；不是当前最小改动 |
| [D：通用快照根引用](candidates/snapshot-references.md) | 坐标不随 tip 移动；不把 ObjectId 误当全库地址；区分引用值与依赖管理 | 已保存的 State-only 模板/配置需要固定版本引用，没有自然事实 Event | 本轮收窄为 Event 根；State 根往往还需 prior 链/完整 Normalize，新增角色和持久 phantom T 尚无消费者要求 |
| [E：应用最小方案](candidates/consumer-minimum.md) | Settings/Calls/Results/中断/纯内存模式的完整清单与真实验收问题 | 仅一应用先证伪机制，最少上游改动即可验证收益 | 作为对照与接入合同；不用 hex string 作为最终库表示，也不要求冷开预热所有有效正文 |

共同目标是实际减少持久正文副本、恢复一致且总成本可接受。EventRef 的“State 捕获图不含正文”是本路线的额外验收，不是对所有候选的统一资格要求：C 仍可捕获字符串，再通过物理内容帧共享使正文只落一份。C 还保留现有 Agent Schema/StateMachine/Replay/属性形状，不让 State 读取依赖某个 Event 包装模型；这些收益必须与底层格式、闭包和故障接线成本一起比较。不同 Event 再次包含同一长串时 C 可能共享而 EventRef 不共享；参数同时作为 JSON 转义子串和另一整串时，C 无法按整串消除重叠，EventRef 的响应投影可以消除这一 State 副本。

## 影响推荐结果的具体分歧

### 值类型与专用外部边

B 的原生字段形状可以保存前发现无效引用、声明目标名义类型，但需要 Schema/SG/visitor 与保存阶段接线，并反复检查外部位置。A 与后续收敛的 D 找到普通 inline 的现成证据：DG 内部 `ObjectHeadLocator` 使用三个 UInt32，`CrossAssemblyGraphTests` 有泛型 `Phantom<T>`。主线程核对了这些源码。

因此最小方案无需恢复图共享或新造 TypeTag。不过普通值的保证确实较弱：State 保存不验证每个外部目标，默认值可以被保存，目标损坏到解析时才发现。推荐稿明确承认这一点，并由 Agent 在启动实际操作前校验依赖；没有把“功能更小”写成与 B 的强完整性等价。

### 非泛型 EventRef 与 EventRef<T>

泛型引用的价值是编译期表达期待类型；它仍不证明实际位置正确。泛型 inline 不是不可行，但当前实例格式只需坐标，异构历史本来就有业务消息变体，持久 phantom T 会增加名义闭合与演化关系。先由 `LoadEvent<T>` 和业务条目承担类型检查；若实际误用频繁且静态约束有明确收益，再调整引用公开形状。

### Event 中能否出现引用

B 主张禁止，D 首稿也倾向禁止以保事件独立。交叉质询后，D 区分了普通字段值与需要库扫描的外部图边：首片若复用普通 inline，禁止某个根角色下的任意嵌套字段需要新机制。

最终不增加这种禁止。Event 含地址时，恢复记录本身仍独立；业务内容不再保证单图闭包。库不递归解引用、不预建依赖图，未来导出/保留工具必须识别 EventRef。Agent 首片仍只 State→Event；这个选择不会让当前事实正文拆散成链。

### 缓存从哪里来

B 的只从持久读取开始最保守；E 希望直接缓存正常提交的 Event，避免热路径读回。两者都需要识别应用可变性。推荐稿选择：库不缓存调用方 T；应用可以缓存与刚提交值一致的自有不可变投影，无法证明时先读回。不是凭 `record` 或 readonly 字段判定深度不可变。

同时采纳 A 对 D 的交叉审查：长寿命 Session 不应永久持有全部投影，缓存应有预算、逐出与 Reset 清理；保证命中只针对仍驻留项。这个约束不要求 DG 新建共享 prepared-DTO cache。

### 冷开是否预热全部当前 History

E 的一次补齐降低后续业务属性复杂度，但使只看元数据也承担全部正文读取。推荐按操作解析，恢复先验证尾描述数量；需运行模型时加载所选 prompt，需工具时只加载活动响应及必要设置。保留显式集中预热为应用策略，不强制所有 LoadState 解引用。

### 调用选择键与合成提示

D 提醒列表下标不天然跨升级稳定，但不能因此要求当前 CallId 必须全局唯一；主线程核对 Agent 未有这个唯一性准入。推荐采用准确 Event 中的调用顺序号，由该业务 Event/升级维持语义，并检查范围与操作关联，不新增通用子对象寻址。

中断提示是应用新生成的短描述，没有必须外置的大事实。推荐保存描述；若要逐字固定才在中断 Event 中保存新文本。Settings.Instructions 则可能很长，必须随 SessionStartedEvent 引用化，不能以“配置”之名漏掉。

## 复核证据与未验证范围

第一轮五个工作包各写独立文件，不先看其他候选；主线程逐份阅读后形成推荐稿。A 又交叉检查 C/D，确认它们存在真实胜例，补充字符串成本拆分、缓存预算，并指出 CallId 唯一性的额外行为约束。主线程复核了 CommitId、Repository 恢复/重入边界、ObjectHeadLocator、普通值访问器、现有 Agent 所有权和发布时序。

融合稿另交由 B（读取/缓存）、C（竞争路线与测量）、E（消费者）分别反向审查，三者均完成并返回具体反例。主线程复核实际源码后采纳如下修订：

| 复核发现 | 主线程裁决与修订 |
|---|---|
| B：关闭/fault 后旧 view 可能命中成功、miss 才失败；回调也可能靠命中绕过重入 | 所有活 view 在 cache lookup 前统一 guard；已交付纯值快照与活 view 分责，旧 view 不自动重新绑定 |
| B：同一响应下调用 0/1 共用 EventRef 时，局部投影会串缓存；宽类型命中可能跳过窄检查 | 默认缓存完整固定事实投影；局部缓存把种类/选择纳入 key；命中保留业务校验 |
| B：独立恢复不证明任意手写 singleton 工厂深拷贝；default 的拒绝阶段含糊 | 核对 GraphReader/GraphReadContext，限定合规 allocator；default 是读时拒绝，业务必填在操作前校验 |
| E：先解析设置可能掩盖现有多尾拒绝 | 恢复先取最多两个尾描述并验证形状，再加载正文；增加“两尾＋坏引用”零正文读见证 |
| E：读依赖普通异常会被 AgentLoop 当执行失败再追加中断 | 核对 AgentLoop 的 catch 顺序，明确 Agent Session 停用与依赖失败分类；零后续 Event/调用，保持普通无效输入拒绝和网络错误原语义 |
| E：已执行工具后再次读旧调用可能丢掉已知结果 | 预加载操作所需设置/调用/关联并保持到结果提交；Program 启动读取和 Dispatch 外 NextOperation 明确纳入迁移 |
| C：EventRef 专属验收会偏置评选；成本不好时不应先为主路线追加优化 | 明确共同目标，加入应用改造/旧 Event 模型依赖成本；允许直接重访物理去重 |
| C/E：纯 State 冷开和真实 Agent 启动零读取不是同一故事 | P6 分开统计；fork 用 DG 夹具，不暗示单分支 Agent 已有分支产品能力 |
| C：Base 交叉场景不足够具体 | 补充转义长 RawInput、未完成结果批次 Base、长 Instructions 经 Reset/Base/冷开三条见证 |

复核没有发现需要推翻推荐方向的已证实阻断。它说明草稿中发现的语义缺口已补到合同和实验表，不证明新机制已实现。普通 inline 的包接线、成本与纯内存来源表示仍列为实验待决；不以评委一致代替运行证据。

B/E 对各自问题的定点修订再次确认：文档缺口已闭合，无新增逻辑冲突。主线程检查了 8 份新文档的围栏与 101 个本地链接，以及索引／路线图的 3 个新导航链接；全部可达。最终暂存范围仅这 8 份文档和两处导航，`git diff --cached --check` 通过。没有为本次文档改动运行产品构建或测试。

本轮没有生成 EventRef 产品代码、构建、进程故障实验或性能对照。因此不能声称单次保存已实现、新包登记已可用、冷读取已足够快，或用户现在即可依靠该草稿保存存档。ReadPair 退役的既有验收也不替代这些证据。
