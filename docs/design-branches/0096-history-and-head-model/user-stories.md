# DB-096：从应用故事提炼历史管理能力

> 状态：需求工作稿，2026-10-17；已确认原线只追加、旧点另开、fork 成功立即可见及冷重开继续。DramaBoard 多世界线来自用户明确描述；其他故事标明来源或假设。[应用合同设计稿](application-design.md)优先验证继承 head-history，本文保留 payload 父链的比较推演；尚未选择持久格式或公开 API，也不是实施工单。
> 阅读入口：[概念模型](README.md)。上游术语和已交付适配仍以[接入记录](headstore-adaptation.md)为准。

## 1. 本轮问题与证据边界

先回答“应用希望用户能完成什么、关心哪些结果”，再推导 DG 应提供的功能，最后与内部成本互相取舍。不能先选每分支一个 Head，再把这种映射需要的字段全部转化为产品需求。

本轮最小验收：用具体操作串说明多开局、主动分叉、重复标签、末端预览、关闭重开；每项区分明确需求、推荐默认和待确认项。能够据此判断候选实现是否满足用户，而不要求读者先选父链或 head-log。

这是文档推演，未做 DramaBoard 当前实现调查、性能测量或新功能测试。用户故事的“预期”描述目标，不宣称当前 DG 已支持。

## 2. 主故事：DramaBoard 多世界线

### 2.1 用户已经说明的范围

- 多个独立开局，例如“中世纪#1”“丧尸末日#4”“废灵根#2”，共同形成森林。
- 应用主动决定何时创建分支，典型触发是关键选择，例如“加入华山派#27”“相信流浪汉#3”。暂不考虑内容寻址、节点合并。
- 分叉后父世界线仍可继续；有子分支的入口也有自己的当前末端和摘要。
- 首版原线只追加；回到旧存档通过另开世界线实现，不需要原线 rewind。
- fork 创建成功即能列出、预览和继续；即使尚未产生新业务存档，也能关闭后重开继续。
- 能枚举历史存档并从选中的旧位置创建新世界线。从 B 的历史视图选中实际属于 A 的存档创建 C，C 直接挂在 A 下，不保存 B 作为业务树的父节点。
- 每级分支有文本标签；标签可以重复，应用自行加编号降低混淆。标签可编辑更好，但不可编辑也能使用。
- 每条世界线末端提供世界摘要，例如角色等级、主要属性、截图缩略图。
- 可以按多级目录或树展示；框架不规定 UI。
- 本故事不要求唯一 branch name，不按显示标签打开世界线，也不要求维护名称到 Head 的唯一绑定。
- 现实玩具交互游戏预计每库世界线不超过 1000；先选根再展开，聚焦最近更新，通常继续上次进度，而非默认展示完整复杂历史。
- 每线存档可能很多，例如每分钟一次；历史长度与世界线数量分别评估。不注册业务模型浏览先顺应实现，不设为硬要求。

这里的“标签”是**显示标签**，不是 DG 的固定历史书签，也不是 HS 的 HeadSetTag。

### 2.2 三种对象先分开

| 讨论对象 | 应用关心什么 | 目前不能直接等同的对象 |
|---|---|---|
| 开局 / 世界线 | 身份、显示标签、来源关系、当前可继续的位置 | HS Head；是否一对一仍是候选 |
| 保存位置 | 某次已保存的领域进展，以及从哪里继续 | 一次目录改名或任意 HeadEntry |
| 预览 | 指定保存位置的摘要和可选缩略图 | 世界线永久属性或完整领域 State |

“开局”先视为没有来源世界线的根，不额外发明一种实体。世界线需要可区分、可在重开后重新定位的身份；它可以复用合适的底层身份，不据此强制增加 `WorldlineId` 类型或外部序列化地址协议。

一条世界线可以有很多次保存；只有应用主动分叉才新增命名分支。展示树的节点数不应自动等于保存次数。至于“世界线”指从根到末端的完整路径，还是某次分叉后的可续写段，仍需在 API 命名前统一；本文用“入口”指用户能选中并继续的对象。

### 2.3 一个贯穿例子

```text
中世纪#1
├─ 加入华山派#27
│  └─ 相信流浪汉#3       [等级 12，所在地域：渡口，缩略图]
└─ 加入华山派#27         [等级 9，所在地域：山门，缩略图]

丧尸末日#4              [生存第 8 天，缩略图]
废灵根#2                [境界：炼气，缩略图]
```

图只表达有标签的来源层级；不规定目录顺序、自动编号、折叠策略或所有存档节点的画法。两个同名兄弟必须可分别选中。图中内部节点也可继续、有自己的摘要，图示仅省略了这些摘要。

用户补充的世界线 `9257` 可呈现为“仙侠-中州-废灵根/加入魔教/遗迹捡到小绿瓶/背叛魔教”，当前存档摘要则类似 `Lv:58,name:林凡,…,screen-shot:'0042:0123cdef'`。前者描述路线语义、相对固定；后者描述当前保存状态、随每次提交一同发布。这里的编号与地址仅为示意，不指定实际编码。

建议按每级局部标签和来源关系组合显示路径；斜杠路径不充当唯一键，也不作为判断祖先关系的依据。是否存整串路径仍可由应用决定，不要求框架解析标签。若支持改名，只改变展示，不重挂分支或改写既有存档。

### 2.4 可观察用户故事

| 编号 | 用户动作与目的 | 预期结果 / 最小验收 | 证据地位 |
|---|---|---|---|
| D1 独立开局 | 创建不同题材的开局，之后从列表继续 | 重开后根可枚举、彼此无业务父关系；重复标签不串线；选中的身份恢复正确领域内容 | 多根和重复标签明确；重开是持久使用的必要验收 |
| D2 主动分叉 | 在关键选择处，从当前或历史保存位置另开路线 | 成功即有独立身份与标签，当前预览复用源存档；无新 State 也可冷重开继续；父子独立推进 | 用户已明确；fork 本身不增加领域存档 |
| D3 逐层浏览 | 从某个开局浏览其子路线，或查看选中路线的来源路径 | 能构建同一棵树，标签重复不改变结构；不依赖反序列化所有世界 State | 树形与预览目的明确；具体分页及读取上限待测 |
| D4 看预览再继续 | 先看等级、地域和小图，再决定加载哪条线 | 列表只取结构与小摘要；缩略图按需读取；选中后才恢复领域对象 | 摘要和缩略图明确；此处推荐将重型加载推迟 |
| D5 保存后的预览 | 推进任一条线并保存，让目录反映新的进展 | 末端及摘要随提交一同发布，路线标签保持自身语义；不能把旧截图静默当作新位置截图 | 一同发布已明确；具体承载仍是候选 |
| D6 更正显示文字 | 把“相信流浪汉#3”改成更有辨识度的名字 | 身份、子路线和既有存档不变；重开保持新文字；不制造新的游戏进展 | 用户偏好，允许延后；不要求保存改名历史 |
| D7 重开并继续 | 退出后再次打开并选择某条路线 | 来源结构、显示文字、末端和预览仍可使用；不依赖上一次进程中的临时映射 | 推荐贯穿验收；不是新增跨库身份要求 |
| D8 从继承历史分叉 | 在 B 中浏览到 A 的旧存档，选择另开路线 C | C 直接挂在 A 下，记录准确分叉位置；A、B 当前末端不变；从哪个视图选中不改变结果 | 用户明确选择；不沿用 workshop 的界面来源语义 |

框架可以验证摘要绑定的是哪个位置，不能验证“等级 12”是否忠实于 State；提取摘要的业务规则由应用负责。缺图可以是合法状态，是否允许异步补图待确认；若允许，必须表达缺失或滞后，不能混淆所属位置。

### 2.5 最影响设计的未决行为

以下都是问题清单，不能自动提升为第一版需求。

| 问题 | 为什么会改变设计 | 暂用工作假设，非用户已选定 |
|---|---|---|
| 历史选择器要显示哪些信息？ | 每次保存附带摘要的候选自然保留旧摘要，但查询规模、附件加载与展示字段仍需界定 | 枚举历史与选点必需；不预设批量加载旧缩略图 |
| 最近更新与上次进度的精确 UI 规则？ | 新空 fork 共享旧存档时间；最近使用不等于最新保存 | 应用先保存选中身份；不为点击追加领域存档，是否需独立创建时间待实际 UI 选择 |

父线继续、历史位置可选、按存档归属建树、首版无 rewind 和 fork 立即可见均已移出未决清单。接下来比较标签的创建承载，并以这些条件检验继承历史能否直接满足需求。

### 2.6 候选细化：一世界线一 Head，Entry payload 显式父链

这是用户此前提出的具体映射，用于检验故事；不表示已选定父链。确认首版无 rewind 后，[并行设计稿](application-design.md)把无额外 Parent 的继承历史列为首选验证候选，本节保留父链作为对照，不构成双轨实施要求。

| 事实 | 候选承载与含义 |
|---|---|
| 世界线身份与相对固定标签 | 身份复用 HeadId；标签归世界线，物理放置仍待选，允许首版创建后固定 |
| 一次领域存档 | 由某个真实保存的 HeadEntryId 标识；payload 包含图入口、`ParentAddress` 和 summary-meta |
| `ParentAddress` | 逻辑基础存档的 HeadEntryId；概念上根无前序，实际 null/哨兵编码待选；不同于 FrameAddress，也不同于同文件上一个物理 Entry |
| 世界线末端 | Head current entry 所表示的逻辑存档；fork 初始克隆须先解释为源存档，不能机械等同当前 EntryId |
| 分支来源 | 创建时选中存档的所属世界线与准确位置；父世界线后来继续不改变该来源 |

可以将 `ParentAddress` 在后续命名时收窄为 `ParentEntryId`，减少与 FrameAddress 的混淆；这里仅说明值的种类，不决定最终公开标识符。

设 A 有存档 `a0 → a1 → a2`，B 从 a2 分叉并保存 b1；用户在 B 的历史列表选 a1 创建 C：

```text
世界线来源：A
            ├─ B，分叉位置 a2，当前 b1
            └─ C，分叉位置 a1，尚无自己的新保存

领域父链：  a0 → a1 → a2 → b1
                  ↘ c1          C 首次新保存后
```

A 可以再保存 a3，B 仍从 b1 继续；C 的初始状态仍来自 a1。B 的历史列表中的 a1 保留 A 的存档身份，故 `ForkHead(a1)` 的来源与业务树一致，不必额外保存“从 B 的界面创建”。共享旧前缀不等于 merge；每个新存档仍只有一个逻辑前序。

**fork 克隆是旧实现中的一条边界。** 原上游基线 `731eef7` 的 `ForkHead(a1)` 会创建新 Entry c0，完整复制 a1 的 payload。若 `a1.ParentAddress = a0`，复制后仍有 `c0.ParentAddress = a0`。直接把 c0 当新存档遍历，会用 c0 替换掉 a1 的准确身份；如果再把来源 a1 插入列表，又会把一次存档展示两遍。

用户已认可现有克隆下的解释：c0 只是新入口对 a1 的初始承接，领域历史中仍显示 a1；首次真正保存 c1 时写 `c1.ParentAddress = a1.Id`，以后 c2 指向 c1。世界线列表保留 C 及其独立标签，即使此时尚无 C 自己的新存档。保留克隆时，身份归一必须依据受检查的 fork 来源与初始条目角色，不能用 payload 相等去重；用户合法地连续保存相同状态仍是两次存档。

后继方案让上游 fork 仅记录准确来源 a1，不产生 c0，直到 C 首次发布才出现本地 c1；已在上游 `474dbe4` 实施，DG 尚未完成新接入验收。领域行为保持相同，复杂性从 DG 过滤转到 HS 的引用初值读取。两者收益、API/格式影响和验证场景集中在[HeadStore 请求 R2](headstore-requests.md#3-r2保留初始克隆还是仅保存来源引用)，旧克隆解释不再是待施工机制。

此规则还有一个应显式验收的推论：从“尚未产生新保存的 C”再分叉，若选中的仍是 a1，新线应同样挂在 A 下；只有选中 C 真正产生的 c1 才挂在 C 下。它与用户选定的存档归属原则一致；创建成功立即可见已经确认，具体实现以上游引用初始化合同为候选。

这份候选尚未完成实施设计；上游请求与 DG 重写边界如下：

1. **定位值的持久化与读回。** 原 R1 已扩为[两类 ID 与准确历史起点的新请求](headstore-save-handles-request.md)，动机见[五个调用故事](save-handle-stories.md)。值可跨 owner 存活不等于可从持久字节解码；不靠反射或每步全历史扫描补齐。
2. **fork 初值的新接入。** 上游已实施引用初始化，由 HS 返回准确源 Entry；DG 接入仍需验收创建、首读、首次保存和 tag 的完整边界，不再重新海选克隆模式。
3. **DG publish 可重写。** 用户明确现有 publish 设计与实现是草稿、预计会重写；GraphEnvelope.Parent 不构成保留或兼容约束。新设计直接选定唯一领域历史关系，无需为旧 Parent 引入同步层。对象 Delta 重建依赖继续与领域前序区分。

该故事暂不要求改名、rewind、修订旧摘要都成为新存档。若标签可改，优先让它独立于存档链；若与保存混用同一 Head，则必须解释非保存发布如何指向既有逻辑存档。允许固定标签，可以让第一轮候选避免这项复杂性。

## 3. 第二个实际方向与对照故事

### C1：有自动保存的状态型编辑器（假设性对照）

用户编辑一份复杂文档，应用频繁保存；用户偶尔“另存一个方案”，并从封面与标题选择继续。很多保存不应变成很多可见分支，改标题不应变成一次领域进展。

它与 DramaBoard 共享“可继续入口 + 保存位置 + 预览”，但不一定需要多级来源树。用它检查 DG 是否强迫简单应用接受唯一分支名、每次存档命名、事件重放或复杂树管理。尚无本轮真实消费者验收，不为它设计专用 API。

### C2：durable LLM Agent tool-loop（用户确认的重要方向）

[DB-083](../0083-checkpoint-api-user-stories/0083-repository-checkpoint-api-user-stories.md) 曾记录 LLM tool-loop，本轮用户进一步确认这是重要应用。具体故事：在细粒度推进中持续保存运行状态，冷重开能知道停在哪一步；从准确旧存档另开分支尝试不同策略，以小摘要选中继续。

应用 State 可表达运行阶段、上下文、待执行意图、已收到结果及消费进度；DG 不预定义这些业务字段。纯 State 连续保存即可成立，Event 可选，既不强制交替，也不以一条 Event 自动证明工具已执行或结果已消费。

冷重开恢复持久状态不等于重放外部工具。工具成功与本地保存之间发生中断时，应用仍需结合幂等键、结果查询等自己的协议判断，DG 不提供跨外部系统 exactly-once。这是能力边界，不扩建 Agent 调度或工具调用框架。

该故事强调当前值读取、细粒度保存和最近少量历史不随累计存档数增长而全链扫描；对象重建成本另算。摘要可以没有截图。应用保存“上次使用哪条线”的偏好，无需为选择动作新增存档。

### C3：Agent RL Gym（远期设想）

用户希望未来能支持，性能越高越好；目前没有确定 workload 或验收指标。它用于保留性能观察方向，不据此要求首片并发 writer、批量事务、GC 或特殊索引，也不将仿真实验当作已经接入的消费者。

### C4：密码门连接多个持续世界（用户提供的候选故事）

主角家中有一扇密码门，不同密码对应不同异世界。人物可带入、带出物品；异世界内部不允许时间回溯。密码到世界 BranchId 的映射由应用维护，不要求用 DG 分支标签作唯一键。

候选组织为一个 Repository 中独立的角色 Branch 与多个世界根 Branch。角色位置、随身物品与某世界物品状态可以在一次 DG 联合提交中共同保存。例如世界失去英雄之剑、角色获得英雄之剑；若穿门位置也受影响，一并更新相应业务 State。每个世界只继续当前进度，不提供选旧 Commit 重获物品的业务操作。

必须共同成立的是业务所有权变化，不只是两个任意状态都保存了。应用负责稳定的物品身份、所属位置和转移规则；DG 的 ObjectId 不是跨独立图的业务物品身份，框架不从两份对象内容自动推导物品守恒。所有需要共同更新的既有分支应能参与同一组；若还要首次创建一个世界，创建与交易的合并是额外协议，不默认属于既有分支联合提交。

这是用户提出的参考需求，尚无消费者实现或运行验收；它为多 Branch 原子发布提供明确动机，但不自动要求跨库事务、分布式服务或并发 writer。

### C5：只携带知识的时间与多世界神器（用户提供的候选故事）

主角可以时间回溯和跨世界往返，但不能携带物品或人物属性；可携带的知识获取幂等，且不受任何遗忘效果影响。候选组织为持续前进的 Knowledge Branch，加上各世界/时间路线 Branch；可回溯的人物属性和物品应归世界路线的 State，不偷偷放入不回退的知识状态。

知识可以建模为按应用定义的稳定事实身份累积的集合：`K' = K ∪ learnedFacts`，重复获知不增加重复条目；在不同世界是否代表同一知识由应用定义。选择旧世界位置时继续采用当前 K，而不是恢复旧 K。DG 不因分支叫 Knowledge 就保证集合单调或拒绝删除，这些是应用保存逻辑的规则。

首片可用“从旧 Commit 新开 Branch，并将应用当前世界选择指向它”表达游戏中的回到过去，旧线仍保留；本故事不自动撤销首片的无原线 rewind 决定。若产品要求同一个 BranchId 的末端倒退，需另开范围。是否原子更新世界选择、知识及世界状态，取决于游戏是否要求知识获得与对应进展共同成立；幂等只能避免重复加入，不能自动弥补丢失的知识保存。

两个故事的共同问题是多个业务状态的组合与共同保存；差别是 C4 允许物品迁移但禁止世界回溯，C5 允许历史路线选择但只迁移幂等知识。暂不要求两者全部进入第一版；[联合提交候选](multi-branch-commits.md)负责提炼存储层合同。

## 4. 从故事提炼的功能集合

以下是候选**能力边界**，不是方法签名清单。

| 能力 | 核心故事需要的最低结果 | 暂不承诺 |
|---|---|---|
| 创建与继续 | 创建独立开局；按身份继续父线或子线；从历史保存位置主动另开路线 | Git 式唯一名称、merge、自动分叉 |
| 结构与历史浏览 | 已接受 ListRootBranches 与 ListBranchSubtree（含起点）的设计入口；枚举历史存档，保留准确归属与分叉位置 | 局部磁盘读取保证、服务端分页、任意图查询 |
| 轻量预览 | 不恢复领域对象即可读取显示文字、末端与小摘要；附件按需 | 任意 JSON 字段索引、全文搜索、缩略图格式规范 |
| 保存与发布 | 新末端及其摘要的关联明确；成功后重开可见 | 所有衍生缓存参与事务、自动保证业务摘要正确 |
| 跨业务分支保存（新候选） | C4 的物品转移或 C5 所需的知识/进展共同成立，仍需明确首片范围 | 自动业务守恒、原线 rewind、新建分支入组、跨库事务 |
| 显示文字维护 | 优选可改名且不改变身份和游戏进展 | 名称唯一、按标签定位、标签历史审计 |

建议先用上述能力评估实现，再决定其中哪些成为 DG 的通用能力、哪些由应用薄适配层组合。领域字段、标签编号和 UI 仍归应用；底层是否增加通用能力，需要独立收益证据。

## 5. 对三个 HeadStore 增强候选的重新定位

### 5.1 小型入口属性：有需求，暂不必固定到 header

明确需求是“小而便于枚举的显示描述”，不是“Head 首帧必须可写 app 字段”。候选至少有：

| 承载位置 | 优点 | 主要代价 / 前提 |
|---|---|---|
| Head 不变 header | 与创建身份一起固定；可只读 header 建索引 | 不能就地改名；加入可变覆盖层后会有两处规则；fork 的新标签也需定义 |
| 每个世界线入口当前 payload 中的描述部分 | 与末端一起获取；可追加更新标签，避免全局大字典 | 依赖世界线到 Head 的映射；保存可能重复少量文字；改名产生非业务 HeadEntry，历史投影须区分 |
| DG 独立属性目录 | 不强制世界线等于 Head；方便统一枚举与修改 | 整体字典首版简单，但冷开、单点读写成本可能随规模增长；未来索引是否必要需测量 |

用户提出的“不变首帧”和“完整反序列化大字典”不是仅有的两端。只解码小描述记录，也不等于恢复业务 State。可先允许一次 O(世界线数) 扫描形成内存索引，但一条线一个文件仍有文件打开成本，不能未经测量称为快速。

### 5.2 保存位置摘要：HeadEntryPayload 已能承载不透明字节

HeadStore 现有 `HeadEntry.Payload` 已是字节；若 DG 选择将图入口、摘要、附件引用编码成一个小描述，**仅为容纳这些内容，不必先增加 HS 的 payload 类型**。领域对象图本体仍可在 FrameStore，不能理解为把整份世界塞进 HeadEntry。

用户已明确摘要归属于每次保存，随提交一同发布；世界线相对固定的标签是另一份信息。候选把存档摘要保存在对应 Entry，当前入口读取当前逻辑存档的摘要，无需再维护一份独立的“最新摘要”权威。剩下要解释改名是否产生非业务 Entry、fork 克隆如何指向源存档，以及截图何时就绪。

缩略图地址只解决定位；所属 FrameStore、内容是否已持久化、读取失败时能否继续显示文字仍待定义。不要求本轮引入独立附件管理框架。

### 5.3 来源查询：先检验现有边集合是否足够

上游已有 `ListHeadOrigins(maxHeads)`：有界扫描全部正式 Head header、检查来源图，返回有来源的边；根无对应边，可以配合 `ListHeads()` 识别。可在内存建 child / parent 索引，计算路径或子树。它不逐边验证 source ticket，不是业务存档可恢复性的证明，也不是按某个根进行的局部查询。

用户已选择按选中存档归属建树；在一世界线一 Head 候选中，向 `ForkHead` 传入该存档的准确 ID，可让两种来源一致。需要确保 fork 初始克隆先归一，且枚举时能区分业务 Head 与框架内部 Head。若以后引入不代表新世界线的 rewind 内部 Head，应重新检验对应关系；当前不为未选功能增加一层来源协议。

### 5.4 不用唯一名称，确实省事；仍要明确完整创建的结果

本故事可以省掉唯一字符串查找与冲突处理，也可以省掉独立名称目录与 Head 的联合发布。**这是真实的简化。**

不过，如果 Head、标签、来源或初始摘要分多个步骤写入，失败后仍需说明哪些对象算正式世界线。比如创建 Head 后、写新标签前中断，目录会显示无名入口，还是暂时不显示？这不是要求再建复杂事务层；若全部必要事实能随一次创建发布，就可能没有第二个发布边界。新 `ForkHead` 引用源存档，不能默认它已同时带上新世界线自己的标签。
