# DB-096：紧凑 Handle 的开发期跨库误用检出能力

> 2026-10-17。用户明确目标是开发期误用检测，不为每个引用支付 16B 完整库身份。主线程复核源码并运行实际置换函数的穷举实验后，接受此目标；撤回[交付复核](headstore-delivery-review.md)中默认要求每个 DG 引用带完整 scope 的建议。
> 不改变上游代码或编码。本记录校准需求与概率解释，不声称强身份、防伪或每个错库调用必定失败。

## 1. 两层检查共同决定检出率

实际函数 `F(x,k)` 是零固定的 XOR 置换：当 x 为 0 或等于 k 时返回 x，否则返回 `x XOR k`。源库编码后，目标库使用自己的 key 解码。

当前合法 LocalHeadId 为 `1..0x00FFFFFF`，因此有两层不同的检查：

1. **编号范围**：解码后不在 24bit 有效域，直接拒绝；仅这一层约检出 255/256。
2. **实际存在性**：即使落进有效域，也需要目标 Head 文件真实存在并通过必要检查。多数编号未使用，进一步检出大量误用。

`TryRead` 只解析字节，`GetLocalHeadId` 只做上下文范围解释，不包含第二层。下面的概率针对实际访问 Head 的路径，而非仅解码或比较两个值。

## 2. 概率与前提

设外来非零 codeword 为 c，目标实际存在的合法 Head 编号集合为 S、大小 N。目标 key 在 UInt32 空间独立均匀，S 的选择与该 key 独立，则：

```text
P(解码到目标已有 Head) = (N + 1[c 属于 S]) / 2^32
                     ≈ N / 2^32
P(范围或存在性检出)   ≈ 1 - N / 2^32
```

原因：对固定 c，普通 XOR 令每个目标编号对应一个 key；保零变体让输出 c 同时对应 key=0 和 key=c，而输出 0 不再出现。所以若 codeword 本身恰是已用局部编号，多一个 key；修正最多为 `1/2^32`。

这直接支持用户的判断：已用 Head 越少，未用 UInt32 编码空间带来的检出能力越强。N 是目标库全部实际 Head 数，含管理 Head；不是只数世界线，也不是编号高水位。

| 实际 Head 数 N | 约漏过范围/存在性检查的概率 | 约检出率 |
|---:|---:|---:|
| 1 | 1 / 4,294,967,296 | 99.9999999767% |
| 1,000 | 1 / 4,294,967 | 99.9999767169% |
| 1,000,000 | 0.0232831% | 99.976716936% |
| 16,777,215（24bit 满域） | 0.390625% | 99.6093750233% |

这不是任意固定库对的随机错误率：同一对库的 key 差固定，映射也固定。若恰好碰到可命中的库对，重复相同误用不会重新抽签；相近编号还可能成批命中。key 高字节相同只说明可能通过范围检查，不能忽略真实文件存在性，也不能把每次调用看作独立 1/256 事件。

对于 HeadEntryId，还必须匹配准确 ticket、长度和已成立发布，因此成功误读的概率不会高于对应 Head 命中概率；但这些检查不是独立随机试验，尤其初始记录的布局可能相同，不能再随意乘一个“地址很长”的概率。

## 3. 实际实验

使用已核对的本地包 `Atelia.Data/0.8.0-persistenthandles-local.20261017105233` 的公开 `ZeroPreservingXor32.Apply`，不是另写替代算法。Release build 为 0 warning / 0 error。

固定 `c = F(123, 0xA5123456) = 0xA512342D`，穷举目标 key 高字节为 `0xA5` 的全部 **16,777,216** 种低位。其余 255 个高字节块由 XOR 高位性质确定全部不通过 24bit 范围，未逐个枚举。

- S=`1..1000`：恰好 **1000** 个 key 命中；总 UInt32 key 空间的比例为 `1000/2^32`。
- S=`1..1,000,000`：恰好 **1,000,000** 个 key 命中。
- S 为完整合法域：恰好 **16,777,215** 个 key 通过。
- 另枚举 65,536 个 key 验证 c=7、S=`1..1000` 时的保零修正，命中为 **1001**。
- 固定两个 key 的差，遍历源/目标的 `1..1000`：差=0 时 1000 个命中，差=1 时 998 个命中，差=512 时 976 个命中，差=1024 时 0 个命中。这验证库对内强相关，不能按独立调用累计置信度。

本机工件：[程序](../../../.artifacts/headstore-misuse-probe/Program.cs)、[结果](../../../.artifacts/headstore-misuse-probe/receipt.json)。这是实际置换函数的编码空间实验，未创建数百万物理 Head，也不是端到端 I/O 错误率或性能测量。文件存在性对照由集合 S 模拟，源代码中的目标定位/记录检查仍负责实际拒绝。

源码依据：[ZeroPreservingXor32](../../../../atelia-storage/src/Data/ZeroPreservingXor32.cs)、[HeadId](../../../../atelia-storage/src/HeadStore/HeadId.cs)、[StoreIdentity](../../../../atelia-storage/src/HeadStore/Internal/Format/StoreIdentity.cs)。正常新建库使用随机 128bit 身份，前4B作为 key，支撑上述独立随机 key 模型；固定镜像和特意选择的库对不满足随机抽样前提。

## 4. 对 DG 设计的修正

1. 按现实约 1000 条世界线、管理 Head 少量的目标，开发期误用诊断足够；不再将强跨库身份作为上游交付阻塞，也不要求为此返工。
2. 默认保留紧凑 HeadId / HeadEntryId。DG 可为世界线/存档角色做薄包装，但不默认每个引用再附加 16B scope。
3. Repository 上下文仍由调用方选择；裸 Handle 的相等只在对应仓库上下文中有意义。跨仓库缓存/集合若确有需要，用集合或外层上下文区分，不把裸 ID 宣称为全局唯一。
4. 应用需要记录“打开哪个仓库”时，可在配置/集合外层保存一次仓库定位信息。是否附完整身份由该具体功能决定，不成为所有存档引用的固定开销。
5. 原 P1 的强身份措辞被用户本轮明确的开发期诊断目标替代。当前上游交付满足收窄后的定位与查询需求；DG 产品接入仍需自己的回归。
