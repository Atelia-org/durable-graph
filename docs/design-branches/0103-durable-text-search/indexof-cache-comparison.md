# VisitSpan 按版本缓存后的字面查找对照

2026-11-19。稳定 memo 条目的默认查找路径建议使用 `VisitSpan` 加 .NET Ordinal。已经展开的多片正文可跨查询复用。已有冻结快照上的 `IndexOf` 及其流式 KMP 仍值得保留。首次搜索大而碎的正文并早停时可跳过全文物化，某些周期文本在相同连续布局上也仍显著有利于 KMP。

## 常驻 memo 语料

下表每格为 ms/次整库查询。前六行是三个进程各自预热后的热路径。KMP 列使用已经取得的同版快照。最后两行分别改变 1 篇、1000 篇后立即计时复扫；每篇一次 Visit 的回调内取八项。

| 碎片篇数 / 总篇数 | 查询 | 快照 KMP | 每篇一次 Visit | 每找下一项重新 Visit |
|---|---|---:|---:|---:|
| 200 / 1000 | 稀疏首项 | 6.89 | 1.03 | 1.06 |
| 200 / 1000 | 每篇早中 | 0.184 | 0.066 | 0.063 |
| 200 / 1000 | 每篇取八项 | 3.94 | 0.57 | 0.47 |
| 1000 / 1000 | 稀疏首项 | 7.15 | 0.92 | 0.90 |
| 1000 / 1000 | 每篇早中 | 0.164 | 0.063 | 0.057 |
| 1000 / 1000 | 每篇取八项 | 4.29 | 0.54 | 0.46 |
| 1000 / 1000 | 只改一篇，再取八项 | 4.24 | 0.60 | — |
| 1000 / 1000 | 每篇都改，再取八项 | 4.42 | 4.04 | — |

原先逐次租还在全碎片语料上，每篇一次和逐项 Visit 分别用 1.38 和 4.11 ms。更新后两种写法都在约半毫秒完成，热查均测得 0 B 托管分配。单次 visitor 还有一项语义优势：所有匹配和摘录都属于进入时的同一版。只改一篇后全扫，Visit 实际分配 **8,024 B**，相当于仅重建那一篇；快照 KMP 八项各查一次，整扫分配 **768,000 B**。[热整库汇总](indexof-cache-results/corpus.csv) · [首次与编辑后汇总](indexof-cache-results/cold.csv)

## 首次查询与缓存成本

1000 篇全部九片时，新版首次展开共分配 **8,024,000 B**，其中 8,000,000 B 是编辑器持续引用的字符载荷。随后同版复访分配 0 B。仅 200 篇碎片时，首次展开共分配 **1,604,800 B**。这里的分配量来自实测，驻留字符载荷按长度计算。不同正文尺寸、活跃的旧版回调及 GC 会改变实际托管堆占用。

同一探针还换回旧包实测。1000 篇全碎片且每篇都在开头命中，新版 Visit 首扫 **3.76 ms**，旧版热池首扫 **1.38 ms**，快照 KMP **0.34 ms**。同版长期复扫时，新版 Visit 已降至上表的 **0.063 ms**。首次扫稀疏命中的全碎片语料，新版 Visit 为 **4.61 ms**，KMP 为 **6.93 ms**。首次取八项的两组初始输入相同，新版 Visit 的三进程中位数分别为 **3.92** 和 **5.75 ms**，相应 KMP 为 **4.31** 和 **4.52 ms**。这个首扫样本的领先方向会翻转。[旧包同口径的版本首次查询](indexof-cache-results/pooled-cold.csv)

大正文的差距更明显。16 篇九片正文，每篇 1,048,576 个 UTF-16 单元，命中位置在开头 8–15 单元。以下全部为**整组 16 篇的耗时**。

| 阶段 | 快照 KMP | 缓存版 Visit | 逐次租还 Visit |
|---|---:|---:|---:|
| 版本首查 | 0.0055 ms | 17.64 ms | 2.73 ms |
| 紧接着再查一次 | 0.0016 ms | 0.0047 ms | 2.39 ms |
| 16 篇全部编辑后首查 | 0.0071 ms | 16.95 ms | 2.50 ms |

缓存版在首查时分配 **33,554,816 B**，紧接着的复查为 0 B。从每篇末前 64 单元起搜时，首查仍要物化整篇，Visit 与 KMP 分别为 **16.95 ms** 和 **0.011 ms**。早中组紧接首查的第二扫，KMP 在三个进程都较快；每批只有 16 次极短查找，绝对值对计时粒度和局部性敏感。

另在持续重复查询**同一篇**的热矩阵中，九片、同为 1,048,576 单元的正文，四字针偏移 8 命中时 KMP / Visit 为 **93 / 26 ns**，近尾起搜为 **265 / 34 ns**，未中为 **1.65 / 0.125 ms**。此前按首项位于篇长 1/32 或 1/16 所观察到的交叉区间，只适用于那次逐次租还实现。[热矩阵](indexof-cache-results/matrix.csv)

## 手写 KMP 的去留

冻结快照可以在编辑器切换版本后继续查询旧正文。流式 KMP 对多片正文可提早停止，空间随针长增长；上面的标准四字针实测为 96 B/次。同版缓存削弱了该路径在稳定 memo 查询上的优势，但对一次性搜索大正文、尤其只需早停或从近尾起搜时，保留差异仍有实际价值。

另有与缓存无关的算法差异。1,048,576 单元的完整单片 `abab…`，1024 单元的周期针在倒数第三个单元失配，KMP 用 **2.25 ms**，Visit 加框架查找用 **53.65 ms**。64 Ki 单片的短针 `aXab` 也是 KMP 较快（**115 / 151 µs**），将失配移到首字符 `Xbab` 后则是框架查找较快（**99 / 7.9 µs**）。建议保留快照实现，把缓存版 Visit 用于常驻编辑器的多次查询。真实请求中各工况所占比例仍待消费方观测。[短针汇总](indexof-cache-results/short.csv)

## 测量口径

受测产品为 `ea8f9236`，本地普通包 `0.1.0-db103.gea8f9236.cd3a3ece0`。独立消费者实际加载的 DLL 与 nupkg 内 DLL 的 SHA-256 均为 `BCE3BE6279D9193188B700C29B83A5CBDE3721C2ECA4E26EABB3D950B01F767B`。性能探针引用这份 DLL，每批原值记录加载哈希。Windows x64、AMD Ryzen 7 1700、.NET 10.0.5，256 位 SIMD，Release，关闭分层 JIT。本次对照使用 Ordinal 字面查找。

- **热路径**沿用[逐次租还版本的矩阵与合成语料](indexof-comparison.md)。先预热每条查询路径，故多片编辑器已有同版缓存。162 个主要工况、40 个追加短针工况和 6 个整库工况分别重跑三个独立进程。各进程内轮换路线顺序，取各批的中位数，再取三个进程的中位数。
- **版本首次查询**为两条路线各建一份相同布局的新编辑器和冻结快照。计时首次全扫、紧接着同版再扫、计时外编辑并取得新版快照后的首次全扫。数字包括字符串物化和查询期间的 GC。构造正文、准备快照、编辑、构造独立 string oracle 及主动清理准备阶段垃圾均在计时外。这里的“首次”指该编辑器版本尚未访问，JIT 已预热。
- **整库语料**含 1000 篇各 4000 个 UTF-16 单元的常驻正文。20% 或 100% 的条目为九片，其余为单片。稀疏首项每十篇仅一篇命中，早中任务每篇均在开头 4–28 单元命中，多项任务每篇取 16 项中的前 8 项。另以 16 篇各 1,048,576 单元的九片正文观察冷缓存的早停和近尾起搜。
- **编辑后**的对照只改原本多片的条目。在全碎片语料额外测只改第 1 篇再扫全库，此时 999 篇仍可复用。每组都移动第 1 篇的首个匹配，校验整库绝对位置的加权和，漏掉失效会得出错误答案。公开快照路径在它自己冻结的同一版本上查找。快照创建和编辑成本不计入搜索时间。

新包共 6066 批。旧包 `8fd71257` 用相同探针在单独进程追加 324 批版本首次查询对照，先预热共享数组池。首次与编辑后扫描前主动 GC，第二次紧随首次，所以两阶段的时间差还包含局部性差异。数据只覆盖已常驻内存的合成正文。仓库读取、真实 memo 命中分布、正则、摘录与工具端到端耗时另行评估。[探针及重跑命令](indexof-probe/README.md) · [新包逐批原值](indexof-cache-results/batches.zip) · [旧包逐批原值](indexof-cache-results/pooled-cold.zip)
