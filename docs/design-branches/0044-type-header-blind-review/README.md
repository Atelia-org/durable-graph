## 2. 已站住的结论

### 2.1 整数寻址与开放/闭合粒度是两个选择

各 reviewer 均支持认真采用仓库内持久整数 token，避免每个对象重复逻辑名称与版本。
逻辑身份、版本和不可变定义仍存在 SchemaStore 中；数字只是指向它们的地址。
同一注册记录可以同时有逻辑索引和数字索引，不必建设另一个 Store 或另一份 Schema 权威。
既有 token 重开保持含义，引用元数据的 State 发布前完成元数据持久；失败残留未引用注册允许。

整数可以标识开放模板，也可以标识整个闭合表示。后者常使重复对象的头更短，但增加闭合登记；
前者复用模板、减少闭合登记，但每个 Base 仍需表达组合。是否再 intern 完整组合是独立的后续取舍。
尚未测量完整目录摊销或解码性能。

### 2.2 postfix 本身不保证更短或更快

同一棵表达式、同一组 token、相同 varint 与相同边界规则，prefix/postfix 的 token 多重集相同，因此长度相同。
prefix 可以根据已知 arity 确定表达式结束；postfix 不能仅看到栈深变成 1 就结束，因为后面还可能接数组操作，须有边界约定。
两种方式都可以迭代解析，不能把 prefix 等同于必须使用 CLR 递归。

主持人用一次性 Python 计数复核了以下示意：内建码 <128、用户 token=128..130，ULEB128；
两边统一加描述字节长度，例中长度均占 1 字节，不计相同对象 envelope。

| 表达式 | prefix token | postfix token | 两者 token 字节 / 加长度后 |
|---|---|---|---|
| Node v1 | `128` | `128` | 2 / 3 |
| Point v2 的 SZ 数组 | `2,129` | `129,2` | 3 / 4 |
| Pair v1 的 int、Point v2 实参 | `130,1,129` | `1,129,130` | 5 / 6 |
| 上述 Pair 的 SZ 数组 | `2,130,1,129` | `1,129,130,2` | 6 / 7 |

相较之下，采用 ASCII 名称、节点 tag、字符串长度、arity、外层版本，以及 builtin 的 kind/tag 两字节，
逻辑 `Node,v1` key 为 8 字节，`Pair<int,Point>,v1` 为 18 字节，均尚未加统一长度或对象 envelope。
这只是指定语法的计数，未包含最终名义/表示槽语法、首次登记、缓存与 reader 绑定成本，不是候选性能基准。

### 2.3 开放模板可以决定历史闭合；不是 ObjectId 类型擦除的障碍

一种尚待机制见证的最小规则为：

```text
Close(不可变版本化模板, 全部 nominal 实参, 实际需要的 exact 值依赖)
    → 完整闭合身份 + 历史 DTO 布局
    → retained reader 的闭合绑定
```

- 所有 nominal 实参都保留，包含 phantom；`Marker<Node>` 与 `Marker<string>` 不能因为 DTO 同为空就混为一个身份。
- 沿本对象的 inline/base 槽递归取得 exact 依赖，遇到引用槽即停止追索目标版本。
- 固定 inline/base 依赖锁在模板内；泛型实参引起的 exact 依赖由闭合描述提供。
- 历史 reader 绑定接收上述完整描述，不能通过 `ObjectId` 或 DTO CLR 类型反猜领域身份。
- 模板及闭合规则是解释来源，求值结果和 reader 缓存是可丢弃派生物；不默认另存完整闭合账本。

这是明确的候选闭合合同，**不是已证明的小实现**。跨泛型 inline/base 依赖传播、旧领域类型删除后的 reader 绑定、
规范编码、错误参数与未知依赖拒绝，都需要共同机制见证。B 保存完整闭合定义也不能省略历史 reader 的绑定证明。

## 3. 两个决定性例子

### 3.1 模板版本与闭合表示身份

```text
Box<T> { T Value; }

C1 = Close(Box模板v1, Point, exact Point v1)
C2 = Close(Box模板v1, Point, exact Point v2)
```

两者的 Box 开放定义没变，但完整表示不同。A 可以直接区分 C1/C2；原 B 的 `(Box<Point>,1)` 不能登记两份布局，
需要提高 owner 版本，或扩展闭合 key、区分模板版本和闭合布局版本。

这不是 B 错读：它会拒绝同 key 冲突。区别是版本治理成本和 Upgrade 身份政策。
若采用 A，**模板版本相同不意味着无需 Upgrade**；owner 必须按完整源/目标闭合表示显式转换，随后用新 Base。
如果改的是 `Carrier<T> { Point Fixed; T Value; }` 中固定 Point 的版本，则模板自身依赖改变，仍须新模板版本。

本项可能改变此前“inline 改版传播外层定义版本”的具体政策，只是研究发现；本轮未更改产品合同或代码。

### 3.2 参数是值类型，不等于它的每次出现都需要 exact 版本

```text
ArrayHolder<T> { T[] Items; }
Slot<T>        { T Value; T[] Items; }
```

当 T=Point 时：

- ArrayHolder 自身只有一个 ObjectId。Point 数组独立升级，不能改变 ArrayHolder 的必要 exact 布局；
  其闭合描述保留 nominal Point，但不能把数组元素版本当作自己的 exact 依赖。
- Slot.Value 内嵌 Point，因此锁定该值的 exact 版本；Slot.Items 仍只持 nominal 数组约束。
- 数组的 Point 版本与 Slot.Value 的 Point 版本是不同来源，不能因为同一领域类型就强制相等。

一位 reviewer 曾建议“所有值参数都携带 exact，phantom 的版本冗余可以接受”，经本例撤回。
若把冗余版本纳入完整布局/Upgrade 身份，就会让仅有引用边的 owner 被动改写；若事后忽略，则另生未定义等价关系。
最小修正是在构造规范闭合描述时，只保留真正进入本对象 inline/base 布局的 exact 依赖。
**这项模板依赖判定是 A 的真实成本，不能用旧的 CLR Type postfix 组合已可用来替代证明。**

## 4. 保留的分歧与主持人判断

| 选择 | 主要收益 | 实际成本 |
|---|---|---|
| 模板 token + 显式闭合描述 | 同模板复用；闭合可重建；模板版本与实参表示演进可分离 | 规范闭合、必要依赖判定、表达式重复、历史求值规则保留 |
| 完整闭合登记 + 整数别名 | 查表得到已固定的完整布局；重复对象头可很短 | 闭合记录登记与目录摊销；必须明确闭合 key/版本政策；reader 绑定仍需实现 |

主持人倾向优先把开放模板 + 完整闭合描述的语义合同写清楚，不将现有“外层定义版本 + nominal key”视为不可改变的前提。
理由是上面的两个例子能把模板自身演进、inline 实参演进和引用目标独立演进分别准确表达。
这不是认定开放方案已经更小、更快；如果闭合规则或历史 reader 绑定变得笨重，应重新评估保存闭合结果的代价。

随后再比较“直接写组合表达式”与“为组合登记一个短别名”。统一描述模型不强迫每个对象都重复写整棵表达式，
也不强迫所有完整布局必须成为另一份持久权威。prefix/postfix 应与这些身份问题分开选择。

## 5. 最小后续验证与本轮证据边界

下一次若进入机制验证，两种方案必须共用同一套开放历史 reader 模板，而不是给某一案预枚举全部闭合 reader。
用 Box、Carrier、ArrayHolder、Slot、Marker、空数组和泛型 base 的有限样本验证：

1. 同一完整描述唯一确定历史 DTO，删除旧领域声明后仍可绑定；重开不借 current 布局。
2. 只改变引用目标版本不改变 owner 的规范布局；改变直接 inline 表示会触发 owner Upgrade/Base。
3. 模板版本相同但闭合表示不同不会跳过 Upgrade；固定依赖改变必须有新模板身份。
4. 以“少闭合、多对象”和“多闭合、少对象”分别计入 Schema 登记及全部对象头字节；解析与绑定性能另测。
