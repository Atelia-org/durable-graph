# 统一盘上不可变容器：storage-2 旁支讨论入口

> 2026-09-30，Discussion / 尚未选型、尚未实施。用户 fork 会话后提出的新架构方向，为上下文压缩保存。可能建立 `atelia-storage-2` 新仓库，通过选择性复制已有代码复用成果；目前没有创建新仓库或实施重构的指令。本记录不替换 DG 主线施工状态，不预先固定名称、程序集、API 或持久格式。

## 用户提出的方向

当前 EventJournal、StateStorage、DurableGraph 各有自己的磁盘 repo 目录、顶层生命周期和发布逻辑；目录相互嵌套，持久数据又跨层引用。用户怀疑这种项目切分本身制造了额外边界协调、恢复复杂性和性能开销，希望从顶层结构消除这些来源。

- 此类项目使用一套统一的磁盘 Repository 结构和程序顶层结构。
- 文件轮转与 BinaryFrame 划分归入共同的 `AddressableNodeAllocator`（暂名）。
- ref、branch、tag 的对外发布归于共同设施。
- 中间层通过 BinaryFrame 所承载的逻辑 Node 直接互相引用，形成不同用途的持久数据结构，承载应用逻辑。
- 整体可理解为“一套盘上版的 Immutable Container”：共享关键基础设施和层级结构，以确定版本的根组合内部数据结构。
- 若旧仓原地修改面过大，考虑另建 `atelia-storage-2`，有选择地复制代码、测试与实验成果，重新选择组件边界。

这是待检验的架构假说：**现有复杂性中，有多少来自多个组件分别拥有 Repository 权威，而统一所有权后能够真正消除？** 新仓库提供试验空间，本身不能证明新模型正确或更简单。

## 压缩前已取得的证据

优先参考[统一根目录与轮转实验](0085-unified-root-metadata-experiment.md)的结论、成本和边界，按具体问题定位代码；不用重新通读 S0 历史或旧评审。

1. 原路线单分支提交已有最后发布 ref 的提交点。新问题集中在目录、分支集合、段选择及多个依赖的共同版本和所有权。
2. 隔离候选已实际替代 catalog/ref/locator 的独立发布权威；真实第二段创建、完整 orphan 保留、恢复再次中断、续写与冷开已验证。它使用真实 EventFrame/Create-ticket 语义，但尚未承载 DG 的真实 Schema/State 图。
3. 统一根没有自动消除成本。无关分支 0→128 时，朴素完整目录每次追加 120→4,216B；候选 writer 准入读取 1,208→612,536B。完整目录版本、重复祖先 reader 和全量恢复资格都是当前原型的实际成本，不能直接推定为所有统一架构的必然成本或已解决问题。
4. 完整 orphan 也有语义约束：不可能的目录 generation、相对已发布前根倒退的 head，不能因 CRC 正确而取得短尾动作资格。共同发布仍需要明确前后版本转换规则。
5. 当前证据限进程故障和明确标记的 F2 模型。新文件内容 flush 与名字/目录持久性是不同责任；尚未提供受控 OS/FS/SSD 的断电保证。用户允许定制部署，候选包括 OpenZFS + 4 SSD。

## 下一轮先讨论的最小模型

先听取用户对整体图景的补充，再用一个具体故事明确所有权：已有分支 A；基于 A 产生新状态并发布 B；写入途中发生一次轮转；在发布前后崩溃，重开后选择一致视图并继续追加。

可以从这张待讨论的责任草图开始：

```text
Repository：资源寿命、独占所有权、确定版本视图、提交/恢复协调
 ├─ 发布设施：ref / branch / tag → 某个版本根
 ├─ 持久 Node 数据结构：目录、Schema、状态、事件历史等
 │    └─ 通过 Node 地址引用其他确定版本的 Node
 └─ AddressableNodeAllocator：帧、物理地址、文件布局与轮转
```

草图没有要求三个程序集、一个文件或一条物理写入流。可以讨论由同一 Repository 管理多个放置区域；关键是它们是否共享生命周期与发布权威。已有 EventJournal/StateStorage 的存储所有权是否消失、哪些业务数据结构仍保留，应逐项说明。

先产出一张小表：**谁拥有事实 → 谁分配地址 → 谁校验引用 → 谁确认持久性 → 谁发布可见版本 → 崩溃后由谁判定**。用它检查是否只是把旧边界换了名字，或又引入第二套“当前状态”。

## 待共同推敲的边界

| 问题 | 要澄清的取舍，不预先冻结答案 |
|---|---|
| Node 与 BinaryFrame | 是否先采用一 Node 一 Frame；大 Node、多个小 Node、类型及版本信息如何影响寻址、校验与读放大？ |
| 地址与分配 | 地址何时可获得、可引用、已持久？地址是物理位置还是稳定身份？保留 orphan 与轮转后如何保证完整记录身份不复用？ |
| 引用结构 | 存储 Node 是否形成 DAG；DG 领域对象的循环引用如何通过局部对象 ID 或批次表达？不能直接把领域对象引用等同于跨帧物理地址。 |
| 根的自举与发布 | ref/branch/tag 目录自己的根如何有界定位和原子选定；谁承担依赖先于根持久及再次故障确认？“不可变”本身不能回答这些问题。 |
| 版本视图 | 子结构只凭根地址能否确定全部依赖，还是还需要 EOF/目录视图？如何避免用后来覆盖的 locator、Schema 目录或索引解释旧根？ |
| 引用可观察性 | 通用设施能否枚举 Node 的持久边，还是需要类型 codec？物理帧、引用和应用语义验证怎样分工，未知 Node 类型怎样报告？它也影响日后 Audit/GC，但当前不据此实施 GC。 |
| 资源与缓存 | 文件、reader、writer lease 和缓存由谁统一拥有？多个容器读取同一 Node 能否共享确定版本的资源，减少重复打开和校验？ |
| 增量成本 | 一次小更新需要重写哪些 Node、目录和根？先明确规模与共享结构，再决定具体持久 map/tree，不能直接把当前全目录复制变成最终格式。 |
| 通用设施边界 | 哪些保障对所有 Node 成立，哪些属于 Schema/状态/历史自身？如何保持规则可组合，避免顶层必须理解所有业务 payload？ |

一次只收口一个关键边界，再用最小反例检验。本旁支允许重新选择组件所有权和仓库结构，不自动执行“把上一实验移植进 DG”的主线下一步。

## 复用成果与保留约束

- 候选复用清单：RBF framing/CRC、顺序 writer、固定 EOF reader、连续前缀检测、故障 hook/外部 Kill 宿主、计量工具及反例。先核对假设，再决定复制范围；机制复用不自动继承旧 repo 嵌套和发布协议。
- Schema/State codec、图恢复和生成器已有大量成果，具体保留位置等新 Node/引用/所有权合同明确后再判断。
- 已有项目正常持久帧仍 append-only；现有 rescue 的独占、旧缓存关闭、全新打开纪律继续有效。新设计若调整地址寿命、回收或修改范围，需明确讨论，不能随复制代码悄悄改变。
- 完整事实、物理完整帧、已发布状态和已回包提交必须区分。读到完整根不证明其自身 flush 已完成；异常、取消和检查未完成不得冒充恢复成功。
- Normal 的受控 writer 来源边界不自动成为恢复舍弃数据的资格。若新根/分配协议提供更强的物理成员或前沿证据，需要新的具体证明。
- 会话 fork 不表示 Git worktree 或文件系统已经隔离。未来建仓/复制/实施前先核对两仓和目标目录；保留主线全部 working tree，不操作真实存档。
