## 一、会影响普通作者或测量可信度的问题

### 1. 源生成器丢失集合元素的可空标注

一个普通项目引用 `Atelia.DurableGraph`，启用 `Nullable=enable`、`TreatWarningsAsErrors=true` 和定义生成。给生成模型加以下字段即可触发，其中 `Page` 是声明节点，`Note` 是注册叶。

```csharp
[DurableField(1)] public List<Page?>? Pages;
[DurableField(2)] public Dictionary<string, Note?>? Notes;
[DurableField(3)] public Page?[]? More;
```

构建在生成的 `DurableGenericStates.g.cs` 报两处 CS8620。回填局部变量写成 `List<Page>` 和 `Dictionary<string, Note>`，写字段的访问器却保留了嵌套的 `?`，两者以 `in` 传递时产生诊断。同一工程的数组字段通过。只把 CS8620 降回警告后，一个进程写入含 null 和重复引用的图，另一个进程成功读回，列表及字典里的别名都正确。这将问题定位在生成的 C# 类型表示。[回填局部变量与字段访问器](../src/DurableGraph.Generator/DurableGraphGenerator.GenericProjection.cs) · [现有注册类型生成回归](../tests/DurableGraph.Tests/RegisteredLeafGeneratorTests.cs)

**最小验收**是让上述普通包项目在严格警告设置下零警告、零错误，并重跑跨进程读写。现有生成测试的 `AssertSchemaOnlyCompiles` 会拒绝编译错误和两种特定警告，CS8620 在默认严重程度下能通过这个断言。可为上述用例单独设严格门禁。修复时只调整需要保留可空性的 C# 声明位置，另核对需要 `typeof` 的位置、持久类型表达式及发布的 Schema history。[测试断言](../tests/DurableGraph.Tests/SchemaOnlyGeneratorTests.cs)

### 2. 私有槽验证会创建没有接收方的值

`DeclaredPrivateFormat<TValue>` 用同一个 `read` 回调验证编码并生成字段值。构造私有格式时会编码并验证默认值，保存时会编码并验证当前值，读 Base 或更新该槽的历史 Delta 时也会验证。上述验证均会丢弃 `read` 的结果。只有最后的回填把结果交给领域对象。若合法的读取器每次创建需要显式释放的对象，作者无从取得验证阶段产生的实例。[格式构造、编码和完整消费检查](../src/DurableGraph/Runtime/Binding/DeclaredPrivateFormat.cs) · [Base 与 Delta 重放](../src/DurableGraph/Runtime/Binding/DeclaredNodeReplay.cs) · [字段回填](../src/DurableGraph/Runtime/Binding/DeclaredMember.cs)

公开 API 见证用一个含单字节值的计数型 `IDisposable`，每次成功解码都创建新实例。构造格式后已解码 1 次，首次保存后累计 2 次。全关冷开、显式释放交付到字段的值后，累计 **创建 4 个解码实例，只释放 1 个**。甚至只构造格式、释放作者传入的默认值，就能观察到额外的一次创建。对普通 `byte[]`，后果是产生可由 GC 回收的临时分配。对需要归还的租约，验证产生的值要有明确的释放方。

**先定合同。** 最小选择是要求验证可无清理地丢弃解码结果，并在公开 XML 和作者示例写明可接受的值。若要支持拥有资源的字段，优先分开“验证字节”与“物化值”，同时规定读取器返回后完整消费检查失败、回填中途失败时谁负责已创建的资源。验收用计数型租约覆盖默认值、捕获、历史 Base、更新私有槽的中间 Delta 和最终交付。须保留对每个历史正文的验证与跨图实例独立性。[私有槽的历史验证](../tests/DurableGraph.Persistence.Tests/RegisteredNodeStoredPrivateTests.cs) · [升级回归](../tests/DurableGraph.Persistence.Tests/DeclaredNodeAppendTests.cs)

### 3. 通用 Release 构建配方实际混入六个 Debug 存储程序集

从干净的 DG 和固定 Storage 源码检出，照依赖指南依次 restore、`dotnet build DurableGraph.slnx -c Release`。构建零警告、零错误，但 Binary、Data、Primitives、Rbf、FrameStore、HeadStore 均输出到 Storage 的 `bin/Debug`。DG 的 Release 测试目录中六个 DLL 的 SHA-256 逐一等于对应 Debug 文件。对照构建加上 `-p:ShouldUnsetParentConfigurationAndPlatform=false` 后，六个文件均与各自的 Release 产物相符。DB-104 实测及 DB-106 主线验收已显式传这个属性，那两次记录与通用指南应分别看待。[通用源码构建说明](../docs/storage-dependency.md) · [DB-104 实测命令](../docs/design-branches/0104-text-editor/mainline-results.md) · [DB-106 验收](../docs/design-branches/0106-container-adapters/README.md#主线验收)

**最小验收**是照更新后的原文从干净的两份检出执行，核对测试输出中六个 DLL 的实际配置与字节。可以先改文档及引用这条配方的性能复现说明。若改成仓库默认传播配置，需验证 Debug、Release 和普通包构建各自的依赖来源。

### 4. 不可能成立的引用槽可以先写入 Schema

声明 `Reference<string>(TypeExpr.List(TypeExpr.Builtin(TypeTag.String)), …)`，让字段初值为 null，注册和首次保存均成功。赋值 `"hello"` 再保存才被拒绝。把持久目标改回正确的 String，同一版本的首次存档又因 Schema 不一致而拒绝冷开。重复引用也有相同触发方式，现有回归还证明失败保存不会追加记录，删除错型成员后可以重试。[声明入口](../src/DurableGraph/Runtime/Binding/DeclaredMember.cs) · [首存、重试及合法数组协变对照](../tests/DurableGraph.Persistence.Tests/DeclaredNodeGraphTests.cs) · [历史共同前缀合同](../src/DurableGraph/Runtime/Binding/DeclaredNode.cs)

这是**作者配置错误发现得太晚**。文档已经要求正确配对，持久读写对非空的错型值也给出了正确拒绝。改进可限于首次使用当前声明时，用已有模型环境提前识别能证明无法赋值的组合。验收应拒绝上述错误的空槽首存，同时允许 `object[]` 访问器接收持久 `string[]`、包按不同顺序登记、节点成环，以及旧版已删除的槽在当前没有对应 CLR 成员。涉及基类或接口时须保留原有可接受的实际目标。[现有持久类型到 CLR 类型的解析](../src/DurableGraph.Persistence/ModelExecutionEnvironment.cs)

## 二、已经量到的保存、历史和恢复成本

### 5. 查询 Event 的前一个 State 会重复扫描纯 Event 前缀

`GetPreviousState(eventId)` 先验证选点确为 Event，再用严格前驱入口直接扫描历史。已有另一路能复用“到此尚无 State”或最近 State 的证明。对一个已验证的 Event，从自身开始找 State 与从父位置开始找，结果相同。[公开入口](../src/DurableGraph.Persistence/Repository.cs) · [最近 State 缓存与严格扫描](../src/DurableGraph.Persistence/RepositoryResources.MetaBootstrap.cs)

实验从一个纯 Event 根开始，每追加一个 Event，在同一位置先调用 `GetPreviousState`，再调用 `LoadLatestSavedState`。32 次均返回没有 State，两种调用分别累计访问 **560 项与 64 项**。指标取自每次公开调用前后的 `HistoryScanVisitedEntries` 差值。建议只调整已经确认是 Event 的调用点。验收覆盖纯 Event 前缀、首个 State、从旧 Event 分叉、错误角色、已停止的仓，以及有 State 时返回的准确 ID。底层以 State 为锚查严格前驱的结果仍须排除自身。[严格前驱和缓存安全回归](../tests/DurableGraph.Persistence.Tests/NearestStateMemoSafetyTests.cs)

### 6. 读取 typed Base 时，为去掉类型头复制整块正文

`TypedBaseBodyCodec.Decode` 解析类型头后，对剩余字节调用 `ToArray()`。同步 reader 随后通过 `IStateBodySource.GetBody(0)` 读取这份数组。同一条链的 Delta 已直接从记录取得只读 span，链本身拥有稳定的记录字节。[解头和同步正文来源](../src/DurableGraph.Persistence/StoredGraphBodies.cs) · [记录的字节所有权](../src/DurableGraph.Storage/ObjectVersionRecord.cs)

实际落盘的 String 与 `List<int>` 各有 262,147 B 正文，类型头分别为 3 B 和 5 B。对各自记录单独解头，分别分配 **262,176 B 和 262,584 B**。在同一 Store 热开含两者的图，整次 `OpenGraph` 平均分配 2,215,506 B。两次独立进程的分配数相同。建议由解头返回布局与正文起点，令同步 reader 从所持记录切片。验收对照大小两档正文、三种路由、旧 Base 加多代 Delta、来源 Schema 和独立物化。大正文应省去与长度相当的一次复制。端到端耗时需另测。

### 7. 文本末尾改一个字，准备 12 B Delta 可能先扫过整篇

给 1,048,576 个 UTF-16 单元做 512 处分散等长替换，冻结时有 1,025 片。模拟保存接受，下一次编辑先把正文压平，再分别在首尾替换一个字。两组都有准确前驱，生成的 Delta 都是 12 B，逐字重放正确。两次独立进程中，改首字后准备 Delta 为 **0.30–0.51 µs**，改末字为 **153–281 µs**。这段计时只包括编码器准备 Delta。等长修改先进入 `ContentEquals`，末尾差异要读完整个相等前缀。[比较与范围编码](../src/Text/TextBodyCodec.cs) · [快照逐片相等比较](../src/Text/TextSnapshot.cs)

可在前驱 token 准确时，跳过来源偏移与输出偏移都一致的 Copy，只检查其余范围。需要保住“编辑后又改回原文”的零变化识别，以及同一 CLR 编辑器被两个图交错保存时的准确前驱。验收要覆盖首尾等长编辑、错位 Copy、同文全替和跨图情况，并核对 Delta 重放及包含接受收据消费的完整保存周期。[净零与错前驱回归](../tests/Text.Tests/TextBodyCodecTests.cs) · [共享编辑器的真实仓库回归](../tests/DurableGraph.Persistence.Tests/TextEditorIntegrationTests.cs)

### 8. 小图热保存也为已登记的 Schema 重建目录索引

其他图先给共享目录引入不同数量的布局，再只保存同一个单行 `Entry`，每次仅改一个整数。`SchemaCatalogWorkspace.PrepareOwned` 对已有目录校验并创建 Builder，Builder 会复制行表、重建索引。到 `Finish` 才返回原 view。各组都没有 Meta 写入。[目录准备、Builder 与零新增出口](../src/DurableGraph.Persistence/SchemaCatalogWorkspace.cs)

| 已登记描述符 | Meta 行数 | 单独准备目录的分配/次 | 整次 SaveGraph 分配/次 |
|---:|---:|---:|---:|
| 1 | 12 | 11,304 B | 45,156 B |
| 18 | 241 | 48,008 B | 130,488 B |
| 66 | 337 | 51,368 B | 144,000 B |

两次进程得到相同的分配数，整次保存还包含捕获、写规划和安装。先验证能否在显式请求、捕获的完整布局及其依赖都精确命中当前已验证目录时复用原 view。验收在保持活图不变的情况下扩大无关目录，另外覆盖新增容器、显式待保存声明和同名同版异形冲突。后两者尤其不能被“按名字命中”的捷径吞掉。[目录语义](../src/DurableGraph.Persistence/SchemaCatalogSemantics.cs) · [完整 Schema 闭包回归](../tests/DurableGraph.Persistence.Tests/MetaBootstrapSchemaClosureTests.cs)

### 9. 同 Schema 的小图反复打开，会重建读取环境

在同一仓轮流打开 16 个同 Schema、仅有两个字段的小图，预热后测 128 次，`OpenGraph` 平均分配 **118,472 B/次**。对同一个已存图，单独运行同一 `ReadStoredGraph` 内核，每次重建环境分配 95,713 B，传入已有准确环境则为 10,632 B。独立重跑得到相同字节数。DB-102 已在单 Event 读取中按准确 Schema 地址复用环境。[图堆入口](../src/DurableGraph.Persistence/Repository.GraphHeap.cs) · [读取内核](../src/DurableGraph.Persistence/DecodedRevision.cs) · [Event 先例及门禁](../tests/DurableGraph.Persistence.Tests/RepositoryModelEnvironmentTests.cs)

适合用同一世界连续查询多条短 memo 的实际访问轨迹复测。最窄的方案先复用同 Store、同冻结配置和相同 Schema 地址的已验证目录。每个可编辑 builder 从恢复到后续保存，须沿用生成自身基线的 `Models` 和 `SelectedSchemaView` 实例。传整个环境的内核差额只给出成本参照。验收看公开入口的分配与常驻成本，同时覆盖新旧 Schema 交替、读取失败、故障或关闭后释放缓存、两个 builder 的可变实例独立性及各自后续增量保存。[可编辑基线的身份检查](../src/DurableGraph.Persistence/BusinessPersistenceAdapter.cs)
